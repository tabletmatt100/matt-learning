Classical ML Evaluation Practical

Dealing with Class Imbalance in Classification

TL;DR

  • Accuracy is useless when one class is rare. A model that always says "not fraud" scores 99% on a 1% fraud problem. Look at precision, recall, PR-AUC and MCC instead.
  • Fix your evaluation first: stratified splits, an untouched test set, and any resampling done only inside the training folds.
  • Moving the decision threshold away from 0.5 is usually the cheapest and most effective fix. With costs, the optimal threshold is $C_{FP}/(C_{FP}+C_{FN})$, assuming calibrated scores.
  • Class weights and focal loss change what the model pays attention to during training. They are cheap and usually beat resampling.
  • SMOTE and friends sometimes help, often do nothing, and occasionally hurt (high dimensions, categorical features, overlapping classes).
  • Resampling and weighting distort predicted probabilities. If you need real probabilities, correct for the prior shift or recalibrate on untouched data.

Most real classification problems are lopsided. Fraud, churn, disease screening, defect detection, click prediction, rare intents in a chatbot. The class you actually care about is the rare one, and standard training and evaluation quietly optimise for the common one.

I'll use one running example throughout: a card-fraud model scoring 10,000 transactions, of which 100 are fraud. That's a 1% positive rate, or a 99:1 imbalance. Real fraud rates are often lower than that, which only makes everything below worse.

1. Why accuracy lies

Start with the laziest possible model: predict "legit" for every transaction. It gets 9,900 out of 10,000 right. That's 99% accuracy, and it catches zero fraud. If your dashboard only shows accuracy, this model looks excellent.

Now a real model. Say it flags 400 transactions, and 80 of them are actually fraud. Here's its confusion matrix:

Predicted fraudPredicted legitTotal
Actual fraudTP = 80FN = 20100
Actual legitFP = 320TN = 9,5809,900
Total4009,60010,000

Its accuracy is $(80 + 9580)/10000 = 96.6\%$. Lower than the do-nothing model. Yet this one is obviously more useful: it catches 80% of fraud. Accuracy is dominated by the 9,900 negatives, so it mostly measures how well you handle the easy majority.

The metrics that actually move

Precision: of the things I flagged, how many were real? $$\text{Precision} = \frac{TP}{TP+FP} = \frac{80}{80+320} = \frac{80}{400} = 0.20$$

Recall (sensitivity, true positive rate): of the real fraud, how much did I catch? $$\text{Recall} = \frac{TP}{TP+FN} = \frac{80}{100} = 0.80$$

F1 is the harmonic mean of the two: $$F_1 = \frac{2PR}{P+R} = \frac{2 \times 0.20 \times 0.80}{0.20 + 0.80} = \frac{0.32}{1.00} = 0.32$$

Specificity (true negative rate) $= 9580/9900 = 0.968$. False positive rate $= 320/9900 = 0.032$.

Balanced accuracy averages recall over both classes: $$\text{BA} = \frac{0.800 + 0.968}{2} = 0.884$$ The always-legit model gets $(0 + 1)/2 = 0.5$, which is what it deserves.

The Matthews correlation coefficient uses all four cells and is my default single-number summary for binary problems:

$$\text{MCC} = \frac{TP \cdot TN - FP \cdot FN}{\sqrt{(TP+FP)(TP+FN)(TN+FP)(TN+FN)}}$$

Numerator: $80 \times 9580 - 320 \times 20 = 766{,}400 - 6{,}400 = 760{,}000$.

Denominator: $\sqrt{400 \times 100 \times 9900 \times 9600} = \sqrt{3.8016 \times 10^{12}} \approx 1{,}949{,}769$.

MCC $= 760000 / 1949769 \approx 0.39$. It ranges from $-1$ to $1$, with 0 meaning no better than chance. The always-legit model has a zero in the denominator, and by convention gets 0.

So the same model reads as 96.6% (accuracy), 0.88 (balanced accuracy), 0.39 (MCC) or 0.32 (F1). None of these is wrong. They answer different questions. The ones that punish the 320 false alarms are the ones that match how the fraud team will feel about this model when they have to review 400 cases to find 80.

PR-AUC vs ROC-AUC

The metrics above all depend on a threshold. To compare models before you've picked one, people use areas under curves. ROC-AUC plots recall against false positive rate. PR-AUC (or average precision) plots precision against recall.

The trouble with ROC on imbalanced data is that the x-axis, FPR, divides by the huge number of negatives. Our model's FPR is 0.032, which looks tiny on a ROC plot. But 0.032 of 9,900 is 320 false alarms, four for every real catch. Precision feels that pain directly because its denominator is the flagged set, not the negative set.

The baselines differ too. A random scorer gets ROC-AUC 0.5 regardless of imbalance. A random scorer's PR-AUC equals the positive rate, here 0.01. So a PR-AUC of 0.30 on this problem is thirty times better than random, even though it sounds bad. I report both, but when they disagree on imbalanced data I trust PR-AUC more. ROC-AUC values of 0.95+ are routine on fraud data and tell you very little.

2. Fix the evaluation before the model

Most of the damage I've seen from imbalance isn't from a bad model. It's from evaluation that lies, so you tune toward the wrong thing. Three rules.

Stratify your splits

With 100 positives and a random 80/20 split, the test set gets on average 20 positives, but it could easily get 12 or 28. With 5-fold CV, each fold has roughly 20, and the variance between folds will be large. Stratified splitting forces each fold to have the same positive rate as the whole. In scikit-learn it's StratifiedKFold and train_test_split(..., stratify=y). There is no reason not to do this.

Even stratified, 20 positives per fold means a recall estimate jumps by 0.05 every time one case flips. Report the spread across folds, and consider repeated stratified CV if positives are scarce. If you have time structure (fraud usually does), split by time instead and accept that the positive rate will drift between folds. That drift is real and you want to see it.

Never resample the test set

The test set should look like production. If production has 1% fraud, so does the test set. If you balance the test set to 50:50, precision goes way up (fewer negatives to generate false positives), and you'll ship a model whose precision in the wild is a fraction of what you reported. Accuracy on a balanced test set is just balanced accuracy in disguise, and PR-AUC becomes incomparable to anything in production.

Resample only inside the training folds

This is the classic leakage bug. If you run SMOTE (or random oversampling) on the full dataset and then do cross-validation, synthetic points made from a validation-fold positive end up in the training fold. Duplicated points are worse: the exact same row appears on both sides. The model has effectively seen the answers, and CV scores come out inflated, sometimes wildly.

The fix is to make resampling a pipeline step so it runs fresh on each training fold and never touches the validation fold. imbalanced-learn ships a Pipeline that does exactly this (the sklearn one won't accept samplers).

Code: leak-free resampling inside cross-validation 
from imblearn.pipeline import Pipeline          # not sklearn.pipeline
from imblearn.over_sampling import SMOTE
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import StratifiedKFold, cross_validate

pipe = Pipeline([
    ("scale", StandardScaler()),
    ("smote", SMOTE(k_neighbors=5, random_state=0)),  # fit_resample on train folds only
    ("clf",   LogisticRegression(max_iter=1000)),
])

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=0)
scores = cross_validate(
    pipe, X, y, cv=cv,
    scoring=["average_precision", "f1", "matthews_corrcoef"],
)
for k, v in scores.items():
    if k.startswith("test_"):
        print(k, v.mean().round(3), "+/-", v.std().round(3))

# WRONG (leaks):
# X_res, y_res = SMOTE().fit_resample(X, y)
# cross_validate(LogisticRegression(), X_res, y_res, cv=cv)

The imblearn pipeline only calls the sampler during fit. At predict time it is skipped, so validation and test data pass through untouched.

3. Threshold moving

Here's the thing a lot of tutorials skip: most classifiers don't output classes, they output scores. The 0.5 cutoff that turns a score into a label is a default somebody picked, not a law. On a 1% problem, a perfectly calibrated model will rarely put any transaction above 0.5, because even a suspicious transaction is usually more likely legit than fraud. So at 0.5 it predicts "legit" almost always, and people conclude the model "can't learn the minority class". It often learned fine. The cutoff is just wrong.

In practice, I'd try threshold moving first, before any resampling or reweighting. It costs nothing, doesn't change the model, and doesn't distort probabilities. Pick the threshold on a validation set (never on test).

Picking the threshold from costs

If you can put rough costs on mistakes, the decision becomes simple. Flag a case when the expected cost of not flagging exceeds the expected cost of flagging. With calibrated probability $p$ of fraud:

$$p \cdot C_{FN} > (1-p) \cdot C_{FP} \quad\Longleftrightarrow\quad p > t^* = \frac{C_{FP}}{C_{FP} + C_{FN}}$$

Say a manual review costs about 5 dollars of analyst time ($C_{FP} = 5$), and a missed fraud costs about 200 dollars in chargebacks ($C_{FN} = 200$).

$$t^* = \frac{5}{5 + 200} = \frac{5}{205} \approx 0.024$$

So you should flag anything with more than a 2.4% chance of fraud. That's twenty times lower than the default. If the costs were equal, you'd get $t^* = 0.5$, which is the only situation where the default makes sense.

This assumes the scores are calibrated probabilities (section 7). If they aren't, the formula gives the wrong number, but you can still sweep thresholds on validation data and pick the one with lowest total cost. Without costs, people pick the threshold that maximises F1, or the one that hits a required recall ("we must catch 90% of fraud") or a review budget ("analysts can handle 500 cases a day").

Code: tuning the threshold on validation data 
import numpy as np
from sklearn.metrics import precision_recall_curve

# p_val: validation scores, y_val: validation labels
prec, rec, thr = precision_recall_curve(y_val, p_val)
f1 = 2 * prec * rec / np.clip(prec + rec, 1e-12, None)
best_f1_t = thr[np.argmax(f1[:-1])]   # last point has no threshold

# cost-based sweep (works even if scores aren't calibrated)
C_FP, C_FN = 5, 200
ts = np.linspace(0.001, 0.999, 999)
cost = [C_FP * ((p_val >= t) & (y_val == 0)).sum()
        + C_FN * ((p_val <  t) & (y_val == 1)).sum() for t in ts]
best_cost_t = ts[int(np.argmin(cost))]

# scikit-learn >= 1.5 can do this inside CV:
from sklearn.model_selection import TunedThresholdClassifierCV
tuned = TunedThresholdClassifierCV(base_clf, scoring="f1", cv=5).fit(X_train, y_train)
print(tuned.best_threshold_)

4. Class weights and cost-sensitive loss

Threshold moving changes the decision after training. Class weights change the training itself: errors on the rare class cost more in the loss, so the model spends more capacity separating it. For binary cross-entropy with weights $w_1$ (positive) and $w_0$ (negative):

$$\mathcal{L} = -\frac{1}{N}\sum_{i=1}^{N} \Big[\, w_1\, y_i \log p_i + w_0\, (1-y_i) \log(1-p_i) \,\Big]$$

The "balanced" formula

scikit-learn's class_weight="balanced" sets each class weight to

$$w_c = \frac{n}{k \cdot n_c}$$

where $n$ is the number of samples, $k$ the number of classes and $n_c$ the count of class $c$.

For our fraud data: $n = 10000$, $k = 2$, $n_{\text{legit}} = 9900$, $n_{\text{fraud}} = 100$.

$w_{\text{legit}} = 10000 / (2 \times 9900) = 0.505$

$w_{\text{fraud}} = 10000 / (2 \times 100) = 50$

Total weight per class: $9900 \times 0.505 = 5000$ and $100 \times 50 = 5000$. Each class now contributes equally to the loss, as if the data were 50:50. The ratio $50 / 0.505 = 99$ is just the imbalance ratio.

Effect on one example where the model says $p = 0.3$: if it's fraud, loss $= 50 \times (-\ln 0.3) = 50 \times 1.204 = 60.2$. If it's legit, loss $= 0.505 \times (-\ln 0.7) = 0.505 \times 0.357 = 0.18$. Missing fraud now hurts 330 times more.

"Balanced" is a starting point, not gospel. Full balancing at 99:1 often overshoots: the model starts flagging far too much and precision collapses. I usually treat the positive weight as a hyperparameter and search something like $\{1, \sqrt{r}, r/4, r\}$ where $r$ is the imbalance ratio. With threshold tuning on top, the gap between these is often smaller than you'd expect, since weighting mostly shifts the score distribution and a re-tuned threshold absorbs a lot of that shift.

Focal loss

Class weights scale every example of a class equally. Focal loss (Lin et al., 2017, from the RetinaNet object detection paper) scales by how hard each example is. Write $p_t$ for the probability the model gives to the true class ($p_t = p$ if $y=1$, $1-p$ if $y=0$). Then:

$$\text{CE} = -\log p_t \qquad\qquad \text{FL} = -\alpha_t\,(1-p_t)^{\gamma} \log p_t$$

The factor $(1-p_t)^\gamma$ is near zero for examples the model already gets right, and near one for examples it gets badly wrong. In detection, there are 100,000 easy background boxes per image; individually tiny losses, but together they swamp the gradient. Focal loss turns them down.

With $\gamma = 2$:

Easy example, $p_t = 0.9$: CE $= 0.105$. Factor $(0.1)^2 = 0.01$. FL $= 0.00105$. Cut by 100x.

Hard example, $p_t = 0.1$: CE $= 2.303$. Factor $(0.9)^2 = 0.81$. FL $= 1.865$. Cut by only 1.23x.

Relative to the easy one, the hard example now matters about 80 times more than it did under plain CE.

Focal loss explorer

2.0

My honest take: focal loss earns its keep in dense detection and in deep models with huge numbers of easy negatives. On tabular data with gradient boosting, plain class weights plus threshold tuning are usually just as good and easier to reason about. Also, focal loss pushes predictions away from confident values, so its outputs are miscalibrated by design. $\gamma = 2$, $\alpha = 0.25$ were the paper's defaults; note that the $\alpha$ there weights the positive (rare) class by 0.25, less than the negatives, because $\gamma$ already did most of the rebalancing.

Derivation: the focal loss gradient

Take a positive example ($y=1$), logit $z$, $p = \sigma(z)$, so $p_t = p$ and $\frac{dp}{dz} = p(1-p)$. Ignore $\alpha$.

$$\text{FL}(p) = -(1-p)^\gamma \log p$$

Product rule with respect to $p$:

$$\frac{d\,\text{FL}}{dp} = \gamma (1-p)^{\gamma-1}\log p \;-\; \frac{(1-p)^\gamma}{p}$$

Chain rule, multiplying by $p(1-p)$:

$$\frac{d\,\text{FL}}{dz} = \gamma\, p\,(1-p)^{\gamma}\log p \;-\; (1-p)^{\gamma+1} = (1-p)^{\gamma}\big(\gamma\, p \log p + p - 1\big)$$

Check: at $\gamma = 0$ this is $p - 1$, the familiar cross-entropy gradient. For $\gamma > 0$, both terms are negative (since $\log p < 0$), and the leading $(1-p)^\gamma$ kills the gradient as $p \to 1$. Numerically: at $p = 0.9$, $\gamma = 2$, the gradient is $0.01 \times (2 \times 0.9 \times (-0.105) - 0.1) = 0.01 \times (-0.290) = -0.0029$, against $-0.1$ for CE. About 34x smaller.

Negative examples are symmetric: replace $p$ with $1-p$ and flip the sign of the gradient.

Code: class weights in sklearn, XGBoost, LightGBM and PyTorch 
# scikit-learn
from sklearn.linear_model import LogisticRegression
from sklearn.utils.class_weight import compute_class_weight
import numpy as np

clf = LogisticRegression(class_weight="balanced", max_iter=1000)
w = compute_class_weight("balanced", classes=np.array([0, 1]), y=y_train)
# w -> array([0.505, 50.0]) for 9900/100
clf2 = LogisticRegression(class_weight={0: 1.0, 1: 10.0})  # hand-tuned

# XGBoost / LightGBM: one number for binary problems
import xgboost as xgb
spw = (y_train == 0).sum() / (y_train == 1).sum()          # 99.0
model = xgb.XGBClassifier(scale_pos_weight=spw, eval_metric="aucpr")

# PyTorch, binary: pos_weight multiplies the positive term only
import torch, torch.nn as nn
loss_fn = nn.BCEWithLogitsLoss(pos_weight=torch.tensor([99.0]))

# PyTorch, multiclass: one weight per class
weights = torch.tensor([0.505, 50.0])
loss_fn = nn.CrossEntropyLoss(weight=weights)
# Focal loss for binary classification (PyTorch)
import torch
import torch.nn.functional as F

def focal_loss(logits, targets, gamma=2.0, alpha=0.25):
    """logits, targets: shape (N,); targets are 0./1. floats"""
    ce = F.binary_cross_entropy_with_logits(logits, targets, reduction="none")
    p = torch.sigmoid(logits)
    p_t = p * targets + (1 - p) * (1 - targets)
    alpha_t = alpha * targets + (1 - alpha) * (1 - targets)
    return (alpha_t * (1 - p_t) ** gamma * ce).mean()

5. Resampling: under, over, SMOTE

Resampling changes the training data instead of the loss. It's the approach most people reach for first, and in my experience it should be about third.

Random undersampling

Throw away majority examples until the classes are closer. Going all the way to 100:100 on our data discards 9,800 of 9,900 legit transactions, 99% of your negatives. That's a lot of information about what normal looks like. Partial undersampling (say to 10:1) is more reasonable, and it does have one real advantage: training gets much faster. On a billion-row click log, downsampling negatives is standard practice for that reason alone, followed by a probability correction (section 7).

Random oversampling

Duplicate minority examples. To reach 50:50 here, each fraud row appears 99 times. Nothing is lost, but nothing new is added either, and flexible models (deep trees, k-NN) will memorise those 100 points. For a linear model, oversampling by a factor $r$ is mathematically almost the same as giving the class weight $r$, so you may as well use weights and skip the bigger dataset.

SMOTE

SMOTE (Chawla et al., 2002) creates new minority points instead of copying. For each minority point, find its $k$ nearest minority neighbours (default $k=5$), pick one, and place a new point at a random spot on the line segment between them:

$$x_{\text{new}} = x_i + \lambda\,(x_{nn} - x_i), \qquad \lambda \sim \text{Uniform}(0, 1)$$

Two fraud points with features (amount z-score, hour-of-day z-score): $x_i = (2.0,\ 3.0)$ and its neighbour $x_{nn} = (4.0,\ 1.0)$.

Difference: $x_{nn} - x_i = (2.0,\ -2.0)$.

Draw $\lambda = 0.3$: $x_{\text{new}} = (2.0 + 0.3 \times 2.0,\ 3.0 + 0.3 \times (-2.0)) = (2.6,\ 2.4)$.

The new point is 30% of the way from $x_i$ to its neighbour. It's plausible only if the space between two fraud cases is also fraud-like, which is the assumption SMOTE quietly makes.

Variants, briefly

  • Borderline-SMOTE only oversamples minority points near the decision boundary (those whose neighbourhoods are mostly majority), on the theory that interior points don't need help.
  • ADASYN generates more synthetic points around minority examples that are harder to learn, weighted by how many majority neighbours each has. It can amplify noise if your "hard" points are mislabelled.
  • Tomek links is a cleaning method: find pairs of opposite-class points that are each other's nearest neighbour, and drop the majority one. It sharpens the boundary a little.
  • ENN (Edited Nearest Neighbours) removes points whose class disagrees with most of their $k$ neighbours. More aggressive than Tomek. SMOTE+ENN and SMOTE+Tomek combine oversampling with cleaning.
  • SMOTE-NC handles mixed numeric/categorical features by taking the majority category among neighbours instead of interpolating.

When SMOTE hurts

  • High dimensions. Nearest neighbours become nearly meaningless in hundreds of dimensions, and the segment between two points passes through empty space. Text embeddings and raw pixels are bad candidates.
  • Categorical or one-hot features. Interpolating between "country = FR" and "country = DE" gives a row that's 0.3 French and 0.7 German. Use SMOTE-NC or don't use SMOTE.
  • Overlapping classes. As in the widget, synthetic points land among the majority and teach the model to flag normal behaviour.
  • Strong learners. Several benchmarks (e.g. Elor and Averbuch-Elor, 2022) found that with tuned gradient boosting and a tuned threshold, SMOTE adds little or nothing over doing no resampling at all. It helped most for weak learners like plain decision trees.
  • Probabilities. Like all resampling, it shifts the training prior, so raw outputs overestimate the minority class.

I'm not anti-SMOTE, it just has to beat a weighted baseline with a tuned threshold on your validation folds before I'd keep it. Often it doesn't.

6. Ensembles built for imbalance

Undersampling throws data away. Ensembles get it back by undersampling many times with different random subsets and combining the results. Every majority example gets used by some member.

  • EasyEnsemble (Liu, Wu and Zhou, 2009): draw, say, 10 balanced subsets (all 100 fraud + 100 random legit each), train an AdaBoost model on each, average. 10 subsets touch about 1,000 of the 9,900 negatives; use more subsets to cover more. Each member is cheap to train.
  • BalancedRandomForest: a random forest where each tree's bootstrap sample is drawn so the classes are balanced. Same idea at the level of individual trees. A good, hard-to-break baseline for tabular data.
  • RUSBoost and BalancedBagging follow the same pattern with boosting or arbitrary base estimators.
  • Gradient boosting with scale_pos_weight: not an ensemble of resamples, just a weighted loss inside XGBoost or LightGBM. The usual starting value is $\#\text{neg} / \#\text{pos} = 9900/100 = 99$. Tune it; values well below the full ratio (like 10 or $\sqrt{99} \approx 10$) often do better on precision-heavy metrics. Also switch the early-stopping metric to aucpr, since the default logloss or AUC will be dominated by the negatives.

On tabular problems my default stack is LightGBM or XGBoost, a moderate scale_pos_weight, early stopping on PR-AUC, then threshold tuning. BalancedRandomForest is my second opinion. I rarely end up needing anything fancier.

from imblearn.ensemble import (

)
lgbm.fit(X_tr, y_tr, eval_set=[(X_val, y_val)], eval_metric="average_precision",
         callbacks=[lgb.early_stopping(100)])

7. Getting probabilities back

If you only need a ranking or a yes/no decision with a tuned threshold, you can skip this section. But if anything downstream uses the number as a probability (expected loss, pricing, combining with other models, showing "12% risk" to a doctor), then resampling and weighting have broken it. A model trained on 50:50 data believes fraud is 50% common, and its outputs reflect that belief. Calibration is the property you need to restore.

Prior-shift correction

If the only thing you changed was the class balance (undersampling, oversampling, or class weights), there's an exact fix. Training with positive rate $\pi'$ instead of the true $\pi$ shifts the model's log-odds by a constant. Undo it:

$$\text{logit}(p) = \text{logit}(p') + \text{logit}(\pi) - \text{logit}(\pi'), \qquad \text{logit}(x) = \ln\frac{x}{1-x}$$

Equivalently, in probability form:

$$p = \frac{p' \,\frac{\pi}{\pi'}}{p'\,\frac{\pi}{\pi'} + (1-p')\,\frac{1-\pi}{1-\pi'}}$$

We undersampled to 50:50 ($\pi' = 0.5$). The real rate is $\pi = 0.01$. The model outputs $p' = 0.8$ for a transaction.

Ratios: $\pi/\pi' = 0.01/0.5 = 0.02$ and $(1-\pi)/(1-\pi') = 0.99/0.5 = 1.98$.

Numerator: $0.8 \times 0.02 = 0.016$.

Denominator: $0.016 + 0.2 \times 1.98 = 0.016 + 0.396 = 0.412$.

$p = 0.016 / 0.412 \approx 0.039$.

The model's "80% fraud" is really about 3.9%. Still four times the base rate, so a useful signal, but nowhere near 80%. Check via logits: $\text{logit}(0.8) = 1.386$, $\text{logit}(0.01) = -4.595$, $\text{logit}(0.5) = 0$. Sum: $-3.209$. $\sigma(-3.209) = 0.039$.

For class weights, use the same formula with the implied training prior. Weights $w_1, w_0$ multiply the odds by $w_1/w_0$, so subtract $\ln(w_1/w_0)$ from the logit. "Balanced" weights at 99:1 give $\ln 99 = 4.595$, the same as undersampling to 50:50.

When the shortcut isn't enough

The prior-shift formula assumes the model was calibrated on its training distribution to begin with. Boosted trees, SVMs, focal-loss networks and SMOTE-trained models often aren't, and SMOTE also changes the shape of the minority distribution, not just its frequency. In those cases, fit a calibration map on a held-out set that has the true class balance:

  • Platt scaling: fit a logistic regression $p = \sigma(a s + b)$ on the model score $s$. Two parameters, works with little data. Note that it can learn the prior-shift offset itself (that's the $b$).
  • Isotonic regression: fit any monotone step function. More flexible, but needs more data, and with only a few hundred positives it overfits. With 100 positives I'd use Platt.

Check the result with a reliability diagram and the Brier score, not with AUC (calibration doesn't change ranking, so AUC won't move).

Code: prior correction and calibration 
import numpy as np
from scipy.special import logit, expit

def correct_prior(p_train, pi_train, pi_true):
    return expit(logit(p_train) + logit(pi_true) - logit(pi_train))

correct_prior(0.8, 0.5, 0.01)   # -> 0.0388

8. Other angles

Treat it as anomaly detection

When positives are extremely rare (dozens in millions), or when new kinds of positives keep appearing that look nothing like the old ones, a supervised classifier has little to learn from. Modelling "normal" and flagging deviations can work better: Isolation Forest, one-class SVM, autoencoder reconstruction error, or plain density estimates. These won't beat a supervised model on the fraud patterns you've labelled, but they can catch the ones you haven't. In fraud teams it's common to run both and send the union to review.

Get more minority data

Boring and usually the biggest win. Some ways: extend the time window, pull in related labelled datasets, mine your false negatives (the cases that were caught later by other means), and use active learning to send the most uncertain unlabelled cases to annotators. An extra 200 real positives is worth more than 10,000 synthetic ones.

Data augmentation

For images, audio and text, domain-aware augmentation (crops, flips, noise, pitch shift, back-translation, paraphrasing with an LLM) applied to the minority class is a much better version of oversampling than SMOTE, because the augmented examples stay on the data manifold. Augment only training data, same rule as before.

Two-stage models

Use a cheap high-recall first stage to throw out the obvious negatives (say 95% of traffic), then train a second, more expensive model on what's left. The second stage sees a much less skewed problem: if stage one keeps 95 of 100 frauds and 500 of 9,900 legit, stage two works at about 16% positives instead of 1%. Search ranking and ad systems are built this way. The cost is two models to maintain, and stage one's misses can never be recovered.

Reframe the label

Sometimes the rare class can be decomposed or merged. Predicting "chargeback within 90 days" might be rarer and noisier than predicting a precursor event that's more common. Grouping a dozen rare intents into an "other" class and handling it separately is another version of the same idea.

9. Order of operations

This is roughly the order I go in on a new imbalanced problem. Most projects stop somewhere around step 5.

  1. Decide what a mistake costs. Even rough numbers ("a miss is about 40 times worse than a false alarm") or a constraint ("we can review 300 cases a day") settle most later arguments.
  2. Set up honest evaluation. Stratified (or time-based) splits, a test set with the production class balance, and metrics that see the minority class: PR-AUC, recall at your operating point, precision, MCC. Put the always-majority baseline in the results table.
  3. Train a plain strong model with no tricks. Gradient boosting for tabular, a pretrained backbone for images/text. Look at PR-AUC. Ranking quality is fixed at this point; everything else is about where you cut.
  4. Tune the threshold on validation data, from costs, a recall target, or a review budget. Often this alone solves the problem people were blaming on imbalance.
  5. Try class weights (or scale_pos_weight), searching a few values below and at the full ratio. Re-tune the threshold each time.
  6. Try focal loss if you're training a deep model with masses of easy negatives.
  7. Try resampling (undersampling for speed, SMOTE variants for low-dimensional numeric data, a balanced ensemble) inside the CV pipeline. Keep it only if it beats step 5 on validation.
  8. Fix probabilities if anything downstream needs them: prior-shift correction, then Platt or isotonic on untouched data. Check with a reliability diagram.
  9. Get more positives. Really this belongs in parallel with everything above. Label mining, active learning, augmentation.
  10. Consider reframing: anomaly detection for unseen patterns, two-stage models for extreme skew, or a different label.

One last opinion. "Imbalance" is often blamed for problems that are really about weak features or too few positives in absolute terms. 100 positives at 1% and 100 positives at 0.01% are harder for very different reasons; the second has the same amount of signal but far more chances for false alarms. If PR-AUC from step 3 is close to the base rate, no rebalancing trick will save you, and the next hour is better spent on features or labels.
