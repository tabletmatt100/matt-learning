Class weights and focal loss

TL;DR

  • Class weights multiply each class's terms in the loss. sklearn's "balanced" rule $w_c = n/(k\,n_c)$ gives 0.505 to the 9,900 legit transactions and 50 to the 100 frauds, so both classes carry a total of 5,000.
  • For a linear model, a weight of 99 on each fraud is exactly the same as copying every fraud 99 times. The loss is identical term for term.
  • The most visible effect of weighting is a shift: the log-odds move up by about $\ln(w_1/w_0)$, which is 4.6 for balanced weights. A lot of the "recall jumped" you see at threshold 0.5 is just that shift, and re-tuning the threshold absorbs most of it.
  • Weighted models are not calibrated. A weighted score of 0.67 can mean a real fraud probability of 0.02.
  • Treat the positive weight as a hyperparameter. I search $\{1, \sqrt{r}, r/4, r\}$; full balancing often overshoots.
  • Focal loss scales each example by how hard it is. With $\gamma = 2$ an example at $p_t = 0.9$ loses 99% of its loss. It earns its keep in deep models with huge numbers of easy negatives; on tabular data, weights plus a tuned threshold are usually enough.

The running example, if you've landed here first: a card-fraud model scored on 10,000 transactions, 100 of them fraud (1%, a 99:1 ratio). At its default threshold it gets TP = 80, FN = 20, FP = 320, TN = 9,580. Part 1 covers why accuracy is useless here; part 3 covers moving the threshold after training. This part is about changing the training itself.

1. Weighted cross-entropy

Threshold moving changes the decision after training. Class weights change the training: errors on the rare class cost more in the loss, so the model spends more of its capacity separating it. Start from binary cross-entropy and put a weight $w_1$ on the positive (fraud) terms and $w_0$ on the negative ones:

$$\mathcal{L} = -\frac{1}{N}\sum_{i=1}^{N} \Big[\, w_1\, y_i \log p_i + w_0\, (1-y_i) \log(1-p_i) \,\Big]$$

With $w_1 = w_0 = 1$ this is ordinary log loss. Nothing else about the model changes: same features, same architecture, same optimiser. In most libraries you can also pass a per-row sample weight, which is the general version; class weights are just sample weights that depend only on the label. This is the simplest form of cost-sensitive learning.

Without weights, the 9,900 legit rows dominate. Suppose early in training the model gives every legit transaction $p = 0.05$ and every fraud $p = 0.4$. The legit rows contribute $9900 \times -\ln 0.95 = 9900 \times 0.0513 = 507.8$ to the summed loss. The frauds contribute $100 \times -\ln 0.4 = 100 \times 0.916 = 91.6$. So 85% of the loss, and most of the gradient, is about getting already-easy negatives slightly more right. Widget 4 further down lets you play with those numbers.

With $w_1 = 50$ and $w_0 = 0.505$, a fraud transaction gets $p = 0.1$. What is its weighted loss term (before dividing by $N$)?

2. The "balanced" formula

scikit-learn's class_weight="balanced" (and compute_class_weight) sets each class weight to

$$w_c = \frac{n}{k \cdot n_c}$$

where $n$ is the number of samples, $k$ the number of classes and $n_c$ the count of class $c$.

For the fraud data: $n = 10000$, $k = 2$, $n_{\text{legit}} = 9900$, $n_{\text{fraud}} = 100$.

$w_{\text{legit}} = 10000 / (2 \times 9900) = 10000 / 19800 = 0.505$

$w_{\text{fraud}} = 10000 / (2 \times 100) = 10000 / 200 = 50$

Total weight per class: $9900 \times 0.505 = 5000$ and $100 \times 50 = 5000$. Each class now contributes equally to the loss, as if the data were 50:50. The ratio $50 / 0.505 = 99$ is just the imbalance ratio, and the total weight is still $10{,}000 = n$, so the overall scale of the loss doesn't change.

Effect on one example where the model says $p = 0.3$: if it's fraud, loss $= 50 \times (-\ln 0.3) = 50 \times 1.204 = 60.2$. If it's legit, loss $= 0.505 \times (-\ln 0.7) = 0.505 \times 0.357 = 0.180$. Missing fraud now hurts about 334 times more than the matching legit mistake.

3. Weights vs copying rows

Here's something that took me a while to really believe: for a model trained by minimising a summed loss, a weight of 99 on each fraud row and simply copying each fraud row 99 times (random oversampling to exactly 50:50) give the same objective.

Weighted version: 10,000 rows. Each fraud row $i$ contributes $99 \times \ell_i$, each legit row contributes $1 \times \ell_j$.

Copied version: $9900 + 100 \times 99 = 19{,}800$ rows, no weights. Fraud row $i$ appears 99 times, contributing $\ell_i + \ell_i + \dots = 99\,\ell_i$. Legit rows contribute $\ell_j$ once each.

The two sums are equal for every parameter setting, so they have the same minimiser. For logistic regression in sklearn the objective is $C\sum_i w_i \ell_i + \tfrac12\lVert\beta\rVert^2$, and the data term is a sum, so even the balance against the penalty is the same. Same coefficients, up to solver tolerance.

So for a linear model with a full-batch solver, weighting and naive oversampling are the same thing, and weighting is the cheaper way to do it (10,000 rows instead of 19,800, and non-integer weights like 9.95 are allowed). They stop being identical when:

  • You train with minibatch SGD. Copies change what each batch looks like; weights change how big each step is. A batch of 256 with weight 99 on the 2 or 3 frauds it happens to contain gives spiky gradients.
  • You use trees with count-based rules. A random forest bootstraps rows, and min_samples_leaf counts rows, not weight. In boosting, weights flow into the hessian sums that min_child_weight checks.
  • You copy before splitting. Then copies of the same fraud land in both train and validation, which is plain leakage. Weights can't leak this way. Part 2 has the details.

SMOTE is different again, because it creates new points rather than repeating old ones; see part 5.

You fit two sklearn logistic regressions with the same C: one with class_weight={0: 1, 1: 99}, one unweighted on a copy of the data where every fraud row appears 99 times. What do you expect?

4. What weights do to the scores

If you've ever turned on balanced weights and watched recall jump from 0.80 to 0.95 while precision fell through the floor, this is why. Weighting mostly slides the whole score distribution upward. For a flexible enough model, the best possible weighted prediction at a point where the true fraud probability is $q$ is

$$p_w = \frac{w_1 q}{w_1 q + w_0 (1-q)} \qquad\Longleftrightarrow\qquad \frac{p_w}{1-p_w} = \frac{w_1}{w_0}\cdot\frac{q}{1-q}$$

In words: the odds get multiplied by $w_1/w_0$, so the logit moves up by $\ln(w_1/w_0)$. For balanced weights that's $\ln 99 = 4.595$. For a logistic regression whose true log-odds really are linear, it is literally an intercept shift and nothing else.

A transaction with true fraud probability $q = 0.02$. Balanced weights, $w_1/w_0 = 50/0.505 = 99$.

Unweighted odds: $0.02 / 0.98 = 0.0204$. Weighted odds: $99 \times 0.0204 = 2.020$.

Weighted probability: $2.020 / (1 + 2.020) = 2.020 / 3.020 = 0.669$.

So at threshold 0.5 the weighted model flags it, and the unweighted one (saying 0.02) doesn't. Going the other way, the weighted threshold 0.5 corresponds to the unweighted threshold $t$ where $99 \cdot t/(1-t) = 1$, so $t = 1/(1+99) = 0.01$.

Compare that with the cost-based rule from part 3: if a missed fraud costs 99 times a false alarm, the best threshold on calibrated scores is $C_{FP}/(C_{FP}+C_{FN}) = 1/100 = 0.01$. Same number. Weighting by $w_1/w_0 = 99$ and then cutting at 0.5 is the cost-based threshold baked into training.

That's why, with threshold tuning on top, the gap between weighted and unweighted models is often smaller than you'd expect. The shift is free to undo. What weights can genuinely change is which region of feature space the model fits carefully, since a misspecified model has to compromise somewhere and weights move that compromise toward the frauds. That part can improve PR-AUC, but usually by much less than the before-and-after-at-0.5 comparison suggests.

Derivation: why the odds get multiplied by $w_1/w_0$

Fix a point $x$ with true fraud probability $q$. The expected weighted loss of predicting $p$ there is

$$R(p) = -w_1 q \ln p - w_0 (1-q)\ln(1-p)$$

Set the derivative to zero:

$$R'(p) = -\frac{w_1 q}{p} + \frac{w_0 (1-q)}{1-p} = 0 \;\Rightarrow\; w_1 q (1-p) = w_0 (1-q) p \;\Rightarrow\; \frac{p}{1-p} = \frac{w_1}{w_0}\cdot\frac{q}{1-q}$$

So the population minimiser is the true odds times $w_1/w_0$. Notice only the ratio matters here; the overall scale of the weights affects step sizes and how strong the regularisation is relative to the data, not where the minimum sits. Undoing it is the prior-shift correction covered in part 6: $q = p_w / \big(p_w + r(1-p_w)\big)$ with $r = w_1/w_0$.

A model trained with balanced weights ($w_1/w_0 = 99$) gives a transaction 0.5. Assuming the model is well specified, what would the same model trained without weights say?

5. Choosing the weight, and library gotchas

"Balanced" is a starting point, not gospel. Full balancing at 99:1 often overshoots: the model starts flagging far too much and precision collapses. I treat the positive weight as a hyperparameter and search something like $\{1, \sqrt{r}, r/4, r\}$ where $r$ is the imbalance ratio. For fraud, $r = 99$, so that's $\{1,\ 9.95,\ 24.75,\ 99\}$. Re-tune the threshold for each value and compare on a threshold-free metric or on cost at the tuned threshold, otherwise you're mostly measuring the shift from section 4.

In XGBoost and LightGBM, binary problems take a single number, scale_pos_weight, which multiplies the positive class only. The usual starting value is $\#\text{neg}/\#\text{pos} = 9900/100 = 99$. LightGBM also has is_unbalance, which sets the same thing for you. Pair it with early stopping on aucpr, because the default log loss is dominated by the negatives.

PyTorch has two arguments that look alike and aren't. In BCEWithLogitsLoss, pos_weight multiplies only the positive term, which is what you want. The weight argument multiplies every element's loss regardless of label. In CrossEntropyLoss, by contrast, weight is one value per class. Mixing these up is one of the most common silent bugs I see.

Scale check. Balanced weights give total weight $9900 \times 0.505 + 100 \times 50 = 5000 + 5000 = 10{,}000$, same as unweighted.

pos_weight = 99 with negatives left at 1 gives $9900 \times 1 + 100 \times 99 = 9900 + 9900 = 19{,}800$. Same ratio, but the summed loss is about twice as big, which acts like doubling the learning rate (or, in sklearn, like doubling C). Usually harmless, but worth knowing when a carefully tuned learning rate suddenly diverges.

Code: class weights in sklearn, XGBoost, LightGBM and PyTorch 
# scikit-learn
from sklearn.linear_model import LogisticRegression
from sklearn.utils.class_weight import compute_class_weight
import numpy as np

clf = LogisticRegression(class_weight="balanced", max_iter=1000)
w = compute_class_weight("balanced", classes=np.array([0, 1]), y=y_train)
# w -> array([0.505, 50.0]) for 9900/100
clf2 = LogisticRegression(class_weight={0: 1.0, 1: 10.0})  # hand-tuned

# Any estimator that accepts sample_weight
sw = np.where(y_train == 1, 10.0, 1.0)
clf.fit(X_train, y_train, sample_weight=sw)

# XGBoost / LightGBM: one number for binary problems
import xgboost as xgb
spw = (y_train == 0).sum() / (y_train == 1).sum()          # 99.0
model = xgb.XGBClassifier(scale_pos_weight=spw, eval_metric="aucpr")

import lightgbm as lgb
model = lgb.LGBMClassifier(scale_pos_weight=10)   # or is_unbalance=True, not both

# PyTorch, binary: pos_weight multiplies the positive term only
import torch, torch.nn as nn
loss_fn = nn.BCEWithLogitsLoss(pos_weight=torch.tensor([99.0]))

# PyTorch, multiclass: one weight per class
weights = torch.tensor([0.505, 50.0])
loss_fn = nn.CrossEntropyLoss(weight=weights)
# note: with reduction="mean" this divides by the sum of the
# weights of the targets in the batch, not by the batch size

6. Effective number of samples (aside)

Inverse-frequency weighting assumes the 9,900th legit transaction adds as much as the first. It doesn't: past a point, new examples mostly repeat what the model has already seen. Cui et al. (2019) turned that into a formula. With a parameter $\beta \in [0, 1)$, the effective number of a class with $n$ samples is

$$E_n = \frac{1 - \beta^{n}}{1 - \beta}$$

and the class weight is proportional to $1/E_n$, normalised so the weights add up to $k$. At $\beta = 0$, $E_n = 1$ for every class (no reweighting). As $\beta \to 1$, $E_n \to n$ (inverse frequency). In between, $E_n$ grows like $n$ for small classes and levels off at $1/(1-\beta)$ for big ones.

$\beta = 0.999$, so the cap is $1/(1-0.999) = 1000$.

Fraud, $n = 100$: $0.999^{100} = 0.9048$, so $E = (1 - 0.9048)/0.001 = 95.2$.

Legit, $n = 9900$: $0.999^{9900} = 0.00005$, so $E = (1 - 0.00005)/0.001 = 999.95$.

Raw weights $1/95.2 = 0.01050$ and $1/999.95 = 0.00100$. Their sum is $0.01150$; rescale so the two add to 2: fraud $2 \times 0.01050/0.01150 = 1.826$, legit $2 \times 0.00100/0.01150 = 0.174$.

Ratio $1.826/0.174 = 10.5$. Compare 99 for "balanced". It lands close to $\sqrt{99} = 9.95$, which is a nice sanity check on my habit of trying the square root.

Honestly, on a binary problem this is just a principled-looking way of picking a weight between 1 and $r$, and $\beta$ becomes the hyperparameter instead. It matters more with hundreds of classes and a long tail, which is what the paper was about (it pairs nicely with focal loss there). Widget 1 above computes it for your counts.

7. Focal loss

Class weights scale every example of a class equally. Focal loss (Lin et al., 2017, the RetinaNet paper) scales by how hard each example is. Write $p_t$ for the probability the model gives to the true class ($p_t = p$ if $y=1$, $1-p$ if $y=0$). Then:

$$\text{CE} = -\log p_t \qquad\qquad \text{FL} = -\alpha_t\,(1-p_t)^{\gamma} \log p_t$$

The factor $(1-p_t)^\gamma$ is near zero for examples the model already gets right, and near one for examples it gets badly wrong. $\gamma$ controls how hard it bites; $\gamma = 0$ gives plain cross-entropy back. In one-stage object detection there are around 100,000 candidate boxes per image and nearly all of them are easy background. Each has a tiny loss, but together they swamp the gradient. Focal loss turns them down, which is a soft, automatic version of hard example mining.

With $\gamma = 2$ (ignore $\alpha$ for now):

Easy example, $p_t = 0.9$: CE $= -\ln 0.9 = 0.105$. Factor $(1-0.9)^2 = 0.01$. FL $= 0.01 \times 0.105 = 0.00105$. Cut by 100x.

Hard example, $p_t = 0.1$: CE $= -\ln 0.1 = 2.303$. Factor $(0.9)^2 = 0.81$. FL $= 0.81 \times 2.303 = 1.865$. Cut by only 1.23x.

Under CE the hard example's loss is $2.303/0.105 = 21.9$ times the easy one's. Under FL it's $1.865/0.00105 = 1770$ times. So relative to the easy one, the hard example now matters about 81 times more than it did.

The $\alpha$ term, and why the paper used 0.25

$\alpha_t$ is an ordinary class weight: $\alpha$ for positives and $1-\alpha$ for negatives. The paper's defaults were $\gamma = 2$, $\alpha = 0.25$, which surprises everyone the first time, because 0.25 weights the rare foreground class less than the background (0.75). The reason is that $\gamma$ had already done most of the rebalancing. In their grid, plain CE ($\gamma = 0$) worked best with $\alpha = 0.75$, the intuitive direction; once $\gamma = 2$ had crushed the easy negatives, the best $\alpha$ swung to 0.25. The two knobs interact, so tune them together, and don't copy 0.25 into a problem where $\gamma$ is small.

The other trick in that paper gets less attention but matters a lot in practice: prior initialisation. They set the final layer's bias so the network starts out predicting the base rate for every example, $b = \ln\big(\pi/(1-\pi)\big)$. With $\pi = 0.01$, $b = \ln(0.01/0.99) = -4.595$. With the default bias of 0, every one of the 9,900 negatives starts at $p = 0.5$ with loss $0.693$, and the first few hundred steps are spent just learning that fraud is rare. I do this for any imbalanced neural net, focal loss or not.

Two things surprised me when I first ran these numbers. With the defaults, focal loss with $\alpha = 0.25$ puts about 90% of the loss on the frauds, nearly as much as balanced weights (95%), without any explicit class weighting doing the heavy lifting. And if you push the legit $p_t$ to 0.99, plain CE already gives the frauds the majority, because 9,900 tiny losses aren't so big after all. Imbalance in the loss depends on how easy the negatives are, not just on how many there are.

Derivation: the focal loss gradient

Take a positive example ($y=1$), logit $z$, $p = \sigma(z)$, so $p_t = p$ and $\frac{dp}{dz} = p(1-p)$. Ignore $\alpha$.

$$\text{FL}(p) = -(1-p)^\gamma \log p$$

Product rule with respect to $p$:

$$\frac{d\,\text{FL}}{dp} = \gamma (1-p)^{\gamma-1}\log p \;-\; \frac{(1-p)^\gamma}{p}$$

Chain rule, multiplying by $p(1-p)$:

$$\frac{d\,\text{FL}}{dz} = \gamma\, p\,(1-p)^{\gamma}\log p \;-\; (1-p)^{\gamma+1} = (1-p)^{\gamma}\big(\gamma\, p \log p + p - 1\big)$$

Check: at $\gamma = 0$ this is $p - 1$, the familiar cross-entropy gradient. For $\gamma \gt 0$, both terms are negative (since $\log p \lt 0$), and the leading $(1-p)^\gamma$ kills the gradient as $p \to 1$. Numerically: at $p = 0.9$, $\gamma = 2$, the gradient is $0.01 \times (2 \times 0.9 \times (-0.105) - 0.1) = 0.01 \times (-0.290) = -0.0029$, against $-0.1$ for CE. About 34x smaller.

Negative examples are symmetric: replace $p$ with $1-p$ and flip the sign of the gradient.

Code: focal loss in PyTorch 
# Focal loss for binary classification (PyTorch)
import torch
import torch.nn.functional as F

def focal_loss(logits, targets, gamma=2.0, alpha=0.25):
    """logits, targets: shape (N,); targets are 0./1. floats"""
    ce = F.binary_cross_entropy_with_logits(logits, targets, reduction="none")
    p = torch.sigmoid(logits)
    p_t = p * targets + (1 - p) * (1 - targets)
    alpha_t = alpha * targets + (1 - alpha) * (1 - targets)
    return (alpha_t * (1 - p_t) ** gamma * ce).mean()

# torchvision has the same thing built in:
# from torchvision.ops import sigmoid_focal_loss

# Prior initialisation for the output layer (pi = 0.01)
import math
model.head.bias.data.fill_(math.log(0.01 / 0.99))   # -4.595

8. Which one I'd use

My honest take: focal loss earns its keep in dense detection and in deep models with huge numbers of easy negatives. On tabular data with gradient boosting, plain class weights plus threshold tuning are usually just as good and easier to reason about. On tabular problems my default is LightGBM or XGBoost with a moderate scale_pos_weight (somewhere around 10 for a 99:1 problem), early stopping on PR-AUC, then a tuned threshold.

Whatever you pick, the outputs are no longer probabilities you can take at face value. Weights multiply the odds by $w_1/w_0$, as in section 4. Focal loss is worse in a less tidy way: it stops pushing once an example is "easy enough", so its outputs are pulled away from 0 and 1 and are miscalibrated by design, with no single formula that undoes it. If anyone downstream will multiply your scores by money, recalibrate on held-out data first. Part 6 covers prior correction, Platt scaling and isotonic regression.

And if you're tempted to stack everything (oversampling, balanced weights and focal loss with $\alpha = 0.75$), stop and count how many times you've corrected the same imbalance. Mcq 8 above is that mistake in miniature.
