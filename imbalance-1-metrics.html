Class imbalance · Part 1 Evaluation metrics

Why accuracy lies: metrics for rare classes

TL;DR

  • With 1% positives, a model that predicts "negative" for everything scores 99% accuracy and catches nothing. Accuracy mostly measures how you handle the easy majority.
  • Read the confusion matrix first. Precision, recall, F1, balanced accuracy and MCC are all formulas of its four cells, and each answers a different question.
  • My default single number for a binary problem is MCC. On the running fraud example it reads 0.39, while accuracy says 96.6%.
  • Recall, FPR and ROC-AUC do not change when the class ratio changes. Precision, F1, MCC and PR-AUC do. That is why ROC-AUC looks flattering on rare-event data.
  • A random scorer's PR-AUC equals the positive rate. Always quote PR-AUC next to that baseline.
  • For multiclass problems, macro averaging is the one that won't let a big class hide a tiny one.

Most real classification problems are lopsided. Fraud, churn, disease screening, defect detection, click prediction, rare intents in a chatbot. The class you actually care about is the rare one, and standard training and evaluation quietly optimise for the common one.

The running example for this whole series: a card-fraud model scoring 10,000 transactions, of which 100 are fraud. That's a 1% positive rate, or a 99:1 imbalance. Real fraud rates are often lower than that, which only makes everything below worse.

1. Why accuracy lies

Start with the laziest possible model: predict "legit" for every transaction. It gets 9,900 out of 10,000 right. That's 99% accuracy, and it catches zero fraud. If your dashboard only shows accuracy, this model looks excellent. scikit-learn even ships it as a DummyClassifier, and I fit one on every new problem just to see the bar.

Now a real model. Say it flags 400 transactions, and 80 of them are actually fraud. Here's its confusion matrix (the four cells are named TP, FN, FP, TN):

Predicted fraudPredicted legitTotal
Actual fraudTP = 80FN = 20100
Actual legitFP = 320TN = 9,5809,900
Total4009,60010,000

Accuracy counts every correct prediction, whatever the class: $$\text{Accuracy} = \frac{TP + TN}{N} = \frac{80 + 9580}{10000} = \frac{9660}{10000} = 96.6\%$$

The do-nothing model: $\frac{0 + 9900}{10000} = 99.0\%$.

So the real model scores lower than the do-nothing model. Yet this one is obviously more useful: it catches 80% of fraud. Accuracy is dominated by the 9,900 negatives, so it mostly measures how well you handle the easy majority. People call this the accuracy paradox, though there's nothing paradoxical about it once you count the errors.

The real fraud model is more useful than the do-nothing model, yet its accuracy is lower (96.6% vs 99.0%). What is the plain reason?

2. Metrics built from the four cells

The metrics that actually move

Precision: of the things I flagged, how many were real? $$\text{Precision} = \frac{TP}{TP+FP} = \frac{80}{80+320} = \frac{80}{400} = 0.20$$

Recall (sensitivity, true positive rate): of the real fraud, how much did I catch? $$\text{Recall} = \frac{TP}{TP+FN} = \frac{80}{80+20} = \frac{80}{100} = 0.80$$

F1 is the harmonic mean of the two: $$F_1 = \frac{2PR}{P+R} = \frac{2 \times 0.20 \times 0.80}{0.20 + 0.80} = \frac{0.32}{1.00} = 0.32$$ The plain average would be 0.50. The harmonic mean sits much closer to the weaker number.

Specificity (true negative rate) $= \frac{TN}{TN+FP} = \frac{9580}{9900} = 0.968$. False positive rate $= \frac{FP}{FP+TN} = \frac{320}{9900} = 0.032$. The two add to 1.

Balanced accuracy averages recall over both classes: $$\text{BA} = \frac{\text{TPR} + \text{TNR}}{2} = \frac{0.800 + 0.968}{2} = 0.884$$ The always-legit model gets $(0 + 1)/2 = 0.5$, which is what it deserves.

Notice which denominators these use. Recall and specificity each divide by one true class (100 fraud, 9,900 legit), so they describe the model's behaviour inside that class and ignore how big the classes are. Precision divides by the flagged set, which mixes the two classes. That makes precision the one that collapses as fraud gets rarer, and it's the one the fraud team feels: 400 cases to review to find 80. If they can only review a fixed number per day, the number they care about is precision at k.

The fraud team raises the threshold. The new matrix is TP = 60, FN = 40, FP = 140, TN = 9,760. What is F1?

The bank adds 90,000 more legit transactions to the test set. The model behaves exactly as before on each class, so FP grows tenfold to 3,200 while TP stays 80 of 100. Which metric stays the same?

MCC: one number that uses all four cells

The Matthews correlation coefficient uses all four cells and is my default single-number summary for binary problems. It's the phi coefficient under another name, introduced to machine learning by Matthews in 1975:

$$\text{MCC} = \frac{TP \cdot TN - FP \cdot FN}{\sqrt{(TP+FP)(TP+FN)(TN+FP)(TN+FN)}}$$

Numerator: $80 \times 9580 - 320 \times 20 = 766{,}400 - 6{,}400 = 760{,}000$.

The four sums are the row and column totals: $TP+FP = 400$, $TP+FN = 100$, $TN+FP = 9900$, $TN+FN = 9600$.

Denominator: $\sqrt{400 \times 100 \times 9900 \times 9600} = \sqrt{3.8016 \times 10^{12}} \approx 1{,}949{,}769$.

MCC $= 760000 / 1949769 \approx 0.39$. It ranges from $-1$ to $1$, with 0 meaning no better than chance. The always-legit model has a zero in the denominator ($TP+FP = 0$), and by convention gets 0.

So the same model reads as 96.6% (accuracy), 0.88 (balanced accuracy), 0.39 (MCC) or 0.32 (F1). None of these is wrong. They answer different questions. The ones that punish the 320 false alarms are the ones that match how the fraud team will feel about this model when they have to review 400 cases to find 80.

Why MCC over F1 as a default? F1 ignores TN entirely, and it changes if you swap which class you call positive. MCC treats the classes symmetrically and only gets high when all four cells are good. Chicco and Jurman (2020) make that case at length. F1 is still fine when the positive class is genuinely the only thing you care about and you know it.

Other single numbers you'll run into: NPV, Youden's J, Cohen's kappa

Negative predictive value is precision for the negative class: $9580/9600 = 0.998$. It's always high on rare-event data and rarely tells you much.

Youden's J is $\text{TPR} + \text{TNR} - 1 = 0.800 + 0.968 - 1 = 0.768$. It's just $2 \times \text{BA} - 1$, rescaled so chance is 0. Same information as balanced accuracy.

Cohen's kappa compares observed agreement $p_o$ to the agreement you'd expect by chance $p_e$ given the row and column totals:

$p_o = 0.966$. $p_e = \frac{400 \times 100 + 9600 \times 9900}{10000^2} = \frac{40{,}000 + 95{,}040{,}000}{10^8} = 0.9508$.

$\kappa = \frac{p_o - p_e}{1 - p_e} = \frac{0.966 - 0.9508}{0.0492} \approx 0.31$.

Kappa and MCC usually move together. I prefer MCC because kappa has some odd behaviour when the predicted and true class rates differ a lot, which is exactly the imbalanced case.

3. Comparing models without a threshold

PR-AUC vs ROC-AUC

The metrics above all depend on a threshold. To compare models before you've picked one, people use areas under curves. ROC-AUC is the area under the ROC curve, which plots recall against false positive rate. PR-AUC (or average precision) uses the precision-recall curve.

The trouble with ROC on imbalanced data is that the x-axis, FPR, divides by the huge number of negatives. Our model's FPR is 0.032, which looks tiny on a ROC plot. But 0.032 of 9,900 is 320 false alarms, four for every real catch. Precision feels that pain directly because its denominator is the flagged set, not the negative set.

You can write precision in terms of the two ROC quantities and the positive rate $\pi$, which shows exactly where the class ratio comes in:

$$\text{Precision} = \frac{\text{TPR}\cdot\pi}{\text{TPR}\cdot\pi + \text{FPR}\cdot(1-\pi)}$$

At $\pi = 0.01$: $\frac{0.8 \times 0.01}{0.8 \times 0.01 + 0.03232 \times 0.99} = \frac{0.008}{0.008 + 0.032} = 0.20$. Matches the matrix.

Same model at $\pi = 0.001$: $\frac{0.0008}{0.0008 + 0.03232 \times 0.999} = \frac{0.0008}{0.0008 + 0.03229} = \frac{0.0008}{0.03309} \approx 0.024$.

The ROC point (FPR 0.032, TPR 0.80) didn't move at all. Precision fell by a factor of eight.

The baselines differ too. A random scorer gets ROC-AUC 0.5 regardless of imbalance. A random scorer's PR-AUC equals the positive rate, here 0.01. So a PR-AUC of 0.30 on this problem is thirty times better than random, even though it sounds bad. I report both, but when they disagree on imbalanced data I trust PR-AUC more. ROC-AUC values of 0.95+ are routine on fraud data and tell you very little. Saito and Rehmsmeier (2015) is the usual citation if someone pushes back.

Advanced: why you shouldn't draw straight lines on a PR curve

On a ROC curve, the straight line between two operating points is achievable: flip a weighted coin between the two thresholds and you land anywhere on that segment. On a PR curve that's false. Precision is a ratio, so mixing two thresholds gives a curved path, not a straight one. Davis and Goadrich (2006) showed this, along with the nice result that one curve dominates another in ROC space if and only if it dominates in PR space.

Practical upshot: computing PR-AUC with the trapezoid rule, as in auc(recall, precision), connects points with straight lines and overestimates the area. sklearn's average_precision_score uses a step sum instead, which is why I use it.

A small example: two points at (recall 0.5, precision 0.5) and (recall 1.0, precision 0.1). Trapezoid between them: $0.5 \times (0.5 + 0.1)/2 = 0.15$. Step sum: $0.5 \times 0.1 = 0.05$. Three times the area from one bad assumption.

4. F-beta and multiclass averaging

Two questions come up constantly once you've moved off accuracy. What if recall matters more than precision? And what do I do with more than two classes?

For the first, F1 has a generalisation, the F-beta score, from van Rijsbergen's information-retrieval work. $\beta$ says how many times more you care about recall than precision:

$$F_\beta = \frac{(1+\beta^2)\,P R}{\beta^2 P + R}$$

$F_2$ on the running example ($P = 0.20$, $R = 0.80$): $\frac{5 \times 0.20 \times 0.80}{4 \times 0.20 + 0.80} = \frac{0.80}{1.60} = 0.50$.

$F_{0.5}$, which leans toward precision: $\frac{1.25 \times 0.16}{0.25 \times 0.20 + 0.80} = \frac{0.20}{0.85} \approx 0.235$.

Our model has good recall and poor precision, so $F_2$ likes it (0.50) and $F_{0.5}$ doesn't (0.235). F1 sits between at 0.32.

I'd use $F_2$ for screening, where a miss is much worse than an extra check. But if you can put actual costs on the two error types, skip F-beta and pick the threshold by expected cost instead. That's Part 3.

What is $F_2$ for the running example (precision 0.20, recall 0.80)?

For more than two classes, you compute precision, recall and F1 per class (one-vs-rest), then combine them. The three standard ways give very different answers on imbalanced data: macro (plain mean over classes), weighted (mean weighted by each class's support) and micro (pool all the counts, then compute once). Only macro treats a class with 50 examples as mattering as much as one with 9,800.

Worked example: macro vs weighted vs micro F1 on a three-class fraud problem

Split the fraud into card fraud and account takeover (ATO). 10,000 transactions, rows are the truth, columns the prediction:

Pred legitPred card fraudPred ATOSupport
Legit9,75040109,800
Card fraud451005150
ATO30101050
Column total9,8251502510,000

Per class:

  • Legit: $P = 9750/9825 = 0.992$, $R = 9750/9800 = 0.995$, $F_1 = 0.994$.
  • Card fraud: $P = 100/150 = 0.667$, $R = 100/150 = 0.667$, $F_1 = 0.667$.
  • ATO: $P = 10/25 = 0.40$, $R = 10/50 = 0.20$, $F_1 = \frac{2 \times 0.40 \times 0.20}{0.60} = 0.267$.

Macro: $(0.994 + 0.667 + 0.267)/3 = 0.642$.

Weighted: $(9800 \times 0.994 + 150 \times 0.667 + 50 \times 0.267)/10000 = 0.985$.

Micro: pool everything. In single-label multiclass every error is one FP for some class and one FN for another, so micro precision, micro recall and micro F1 all equal accuracy: $(9750 + 100 + 10)/10000 = 0.986$.

Weighted and micro both say 0.98-something, and both hide the fact that the model misses 80% of account takeovers. Macro (0.64) shows it. In sklearn, f1_score(y, y_hat, average='macro'); the default average='binary' raises an error on multiclass targets.

In the three-class example above, your manager wants one number on the dashboard that will drop if the ATO detector gets worse. Which do you give them?

5. Computing them in scikit-learn

Everything above is one import away. Two things trip people up. The threshold-free metrics need scores (from predict_proba), not hard labels. And confusion_matrix puts the negative class first, which catches out anyone who unpacks it by memory.

Code: computing these metrics in scikit-learn 
from sklearn.metrics import (
    confusion_matrix, precision_score, recall_score, f1_score, fbeta_score,
    balanced_accuracy_score, matthews_corrcoef,
    average_precision_score, roc_auc_score, classification_report,
)

# y_true: 0/1 labels, y_score: predicted probability of class 1
# y_score = model.predict_proba(X_test)[:, 1]
y_pred = (y_score >= 0.5).astype(int)

tn, fp, fn, tp = confusion_matrix(y_true, y_pred).ravel()   # this order!
print("precision", precision_score(y_true, y_pred))
print("recall   ", recall_score(y_true, y_pred))
print("f1       ", f1_score(y_true, y_pred))
print("f2       ", fbeta_score(y_true, y_pred, beta=2))
print("bal acc  ", balanced_accuracy_score(y_true, y_pred))
print("mcc      ", matthews_corrcoef(y_true, y_pred))

# threshold-free: pass scores, never y_pred
print("PR-AUC (avg precision)", average_precision_score(y_true, y_score))
print("random baseline       ", y_true.mean())
print("ROC-AUC               ", roc_auc_score(y_true, y_score))

print(classification_report(y_true, y_pred, digits=3))

Note that average_precision_score is not exactly the trapezoidal area under the PR curve. It's a step-wise sum, which avoids the overly optimistic interpolation you get from auc(recall, precision). Use it.

The classification_report prints per-class precision, recall, F1 and support, plus macro and weighted averages. It's the fastest way to see a minority class being ignored.

Spot the bug. A pipeline ends with:

y_pred = model.predict(X_test)
print(average_precision_score(y_test, y_pred))
print(roc_auc_score(y_test, y_pred))

Both numbers come out lower than expected, and ROC-AUC exactly equals the balanced accuracy. What's wrong?

Spot the bug. On the running example, a script prints "precision 0.968". The code:

6. What I actually report

For a binary imbalanced problem my standard table is: the confusion matrix at the chosen threshold, precision and recall, MCC, and PR-AUC with its baseline next to it. ROC-AUC goes in too, because people ask for it, but I don't make decisions from it. If the business has a fixed review capacity, precision at that k goes at the top.

Two caveats. First, all of these are noisy when the minority class is small. With 20 fraud cases in a test set, one case is 0.05 of recall, and the standard error at recall 0.8 is about $\sqrt{0.8 \times 0.2 / 20} \approx 0.09$. Report a bootstrap interval or use repeated stratified folds (Part 2). Second, if your test set has a different positive rate from production, precision and PR-AUC won't transfer. That's the prevalence shift problem from Widget 3, and it also bites whenever someone resamples the test set, which is a form of leakage covered in Part 2.

Threshold metrics also depend on, well, the threshold, and 0.5 is rarely right for rare classes. Picking it properly is Part 3. If you later reweight or resample the training data (Part 4, Part 5), recheck calibration before trusting any score as a probability (Part 6).

Your test set has only 20 fraud cases. Across reruns with different random splits, recall swings between 0.70 and 0.85, and a teammate's "improvement" raised it from 0.75 to 0.80. What would you do?
