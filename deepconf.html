Deep Think with Confidence (DeepConf)

Notes on Fu, Wang, Tian and Zhao, "Deep Think with Confidence", arXiv 2508.15260, August 2025.

TL;DR
  • Majority voting over hundreds of sampled reasoning traces works, but it is expensive and counts a rambling, lost trace the same as a clean one.
  • DeepConf scores each trace using the model's own token probabilities. The useful score is local: the average confidence over a sliding window of tokens, and especially the worst window in the trace.
  • Offline, it keeps only the most confident traces (top 10% or top 90%) and runs a confidence-weighted vote over them.
  • Online, it generates 16 warmup traces, sets a cutoff from their scores, and kills any new trace the moment its windowed confidence falls below that cutoff. It also stops sampling once the vote is lopsided enough.
  • Reported headline: GPT-OSS-120B on AIME 2025 goes from 97.0% (cons@512) to 99.9%, and online mode cuts generated tokens by up to 84.7%. No training, no per-task tuning, a small patch to vLLM.
  • The weak spot is obvious once you see it: a trace that is wrong but confident sails through the filter.

1. The problem with voting over 512 traces

The cheapest reliable trick for squeezing more accuracy out of a reasoning model is self-consistency. Sample the same math problem many times, read off the final answer of each trace, and return whichever answer shows up most. Papers write this as cons@N, where N is the number of traces. People also call it parallel thinking, since the traces are independent and can run side by side.

It works well enough that it became the default baseline. It also has two ugly properties. First, the cost is linear in N and the accuracy curve flattens quickly, so going from 64 to 512 traces buys you 8x the tokens for a point or two. On reasoning models a single trace can be 10,000+ tokens, so cons@512 on one AIME problem can mean millions of generated tokens. Second, every trace gets one vote. A trace that wandered off, second-guessed itself twenty times and landed on a guess counts exactly as much as one that solved the problem in a straight line.

DeepConf goes after the second problem, and solving it turns out to help with the first. If you can tell which traces are bad, you can drop them from the vote. If you can tell early, you can stop generating them and save the tokens.

The signal they use is the one the model already hands you for free: the log-probabilities of the tokens it considered at each step.

2. How confident is one token?

At each position $i$ the model produces a distribution over the vocabulary. Two standard ways to summarize how peaked it is:

Token entropy, which uses the whole distribution:

$$H_i = -\sum_{j} P_i(j)\,\log P_i(j)$$

And the paper's token confidence, which only uses the top-k tokens:

$$C_i = -\frac{1}{k}\sum_{j=1}^{k} \log P_i(j)$$

Low entropy means confident. High $C_i$ means confident. That second one feels backwards at first, so it's worth working through. When the model is sure, the top token gets nearly all the mass and the other $k-1$ tokens get tiny probabilities. Tiny probabilities have large negative logs, and after the minus sign they become large positive numbers. So $C_i$ is big. When the model is torn, the top-k probabilities are all middling and their negative logs are all moderate, so $C_i$ is small.

Put differently, $C_i$ mostly measures how unlikely the runners-up are, not how likely the winner is. The top token contributes almost nothing. I think that's a slightly odd design, but it's cheap: inference servers already return top-k logprobs, so you never need the full vocabulary distribution.

A scores almost twice as high as B. Look at where A's score comes from: the winning token adds 0.105, and the four runners-up add the other 15.24. For comparison, the entropy over these five tokens is 0.453 nats for A and 1.595 nats for B, so the two measures agree on the ordering here.

One practical note. The absolute value of $C_i$ depends on $k$ and on the model. With a larger $k$ you include even rarer tokens and the numbers climb. That's fine for DeepConf, because it only ever compares traces for the same question from the same model. You can't carry a threshold from one setup to another, and the method doesn't try to.

3. From tokens to traces: global versus local scores

A trace has thousands of token confidences. You need one number per trace to rank them. The obvious choice, used in earlier work, is the mean over all tokens. That's essentially self-certainty, and DeepConf calls it average trace confidence:

$$C_{\text{avg}} = \frac{1}{N}\sum_{i=1}^{N} C_i$$

The problem is that a 12,000-token trace can have a stretch of 300 tokens where the model clearly lost the thread ("wait, let me reconsider... actually no...") and still post a decent average, because the other 11,700 tokens of routine algebra are confident. The breakdown is exactly what predicts a wrong answer, and averaging dilutes it to almost nothing.

So the paper switches to local measures. The building block is group confidence: the mean token confidence over a window $G_i$ of $n$ consecutive tokens, with windows overlapping (one per position).

$$C_{G_i} = \frac{1}{|G_i|}\sum_{t \in G_i} C_t$$

The paper uses windows of 2048 tokens. From the series of group confidences it builds several trace scores:

  • Bottom-10% group confidence: the mean of the lowest 10% of group confidences in the trace.
  • Lowest group confidence: just the minimum. This is the one the online algorithm uses, because you can track it while generating.
  • Tail confidence: the mean token confidence over the final stretch of the trace (they use the last 2048 tokens). The reasoning is that the end of a trace, where the answer gets written down, matters most.

4. Offline DeepConf: filter, then weight

Offline means all the traces are already generated. You just want a better vote. DeepConf does two things.

Confidence-weighted voting. Each trace $t$ with answer $a_t$ and confidence score $C_t$ (any of the trace scores above) contributes $C_t$ votes instead of one:

$$V(a) = \sum_{t \in T} C_t \cdot \mathbb{1}[a_t = a], \qquad \hat{a} = \arg\max_a V(a)$$

Confidence filtering. Before voting, sort traces by $C_t$ and keep only the top $\eta\%$. The paper tries two settings: $\eta = 10\%$ (aggressive, DeepConf-low) and $\eta = 90\%$ (conservative, DeepConf-high).

Here is something the paper's framing glosses over. Raw confidence scores for traces on the same question tend to sit in a narrow band. If one trace scores 13 and another 11, weighting gives the first only 18% more say. That's a weak nudge. The filtering step does most of the work, because it gives low-confidence traces zero say.

Worked example: 8 traces, true answer 24

Scores are lowest group confidence on an arbitrary scale.

traceT1T2T3T4T5T6T7T8
answer1824183024182418
$C_t$10.913.211.312.112.810.613.511.0

Plain majority. 18 gets 4 votes, 24 gets 3, 30 gets 1. Majority returns 18, which is wrong.

Weighted, no filter.

  • $V(18) = 10.9 + 11.3 + 10.6 + 11.0 = 43.8$
  • $V(24) = 13.2 + 12.8 + 13.5 = 39.5$
  • $V(30) = 12.1$

Still 18. The extra wrong trace outweighs the confidence edge. This is the weak-nudge problem in action.

Filter to top 50%, then weight. Keep the 4 highest: T7 (13.5), T2 (13.2), T5 (12.8), T4 (12.1).

  • $V(24) = 13.5 + 13.2 + 12.8 = 39.5$
  • $V(30) = 12.1$

Now 24 wins. Its weighted share is $\beta = 39.5 / (39.5 + 12.1) = 39.5/51.6 = 0.766$.

Filter to top 90%. With 8 traces, 90% rounds to 7, so only T6 (10.6) goes. $V(18) = 43.8 - 10.6 = 33.2$, $V(24) = 39.5$. 24 wins. Even the conservative filter flips the result here, because the dropped trace happened to be one of the wrong ones. With 8 traces that's luck; with 512 the effect is statistical.

Filter to top 10%. One trace survives: T7, answer 24, $\beta = 1.0$. Correct, but now you're trusting a single sample. On a problem where the most confident trace is confidently wrong, this setting fails with no backup.

Pseudocode: offline DeepConf 
input: traces T = {t_1..t_N}, each with final answer a_t
       and token confidences C_{t,1..L_t}
params: window n (2048), keep fraction eta (0.10 or 0.90),
        score in {bottom10, lowest, tail}

for each trace t:
    G = [mean(C_{t,i-n+1..i}) for i in n..L_t]     # sliding group confidences
    if score == lowest:   s_t = min(G)
    if score == bottom10: s_t = mean(smallest 10% of G)
    if score == tail:     s_t = mean(C_{t, L_t-n+1..L_t})

keep = top ceil/round(eta * N) traces by s_t
V = {}                                             # weighted votes
for t in keep:
    V[a_t] += s_t
return argmax_a V[a]

5. Online DeepConf: stop bad traces early

Offline filtering improves accuracy but saves nothing, since you already paid for all 512 traces. The online version uses the same idea to stop paying for traces that are going badly.

It runs in three parts.

  1. Warmup. Generate $N_{\text{init}} = 16$ traces to completion. Compute each one's lowest group confidence.
  2. Set the threshold. Pick $s$ as a percentile of those 16 values. DeepConf-low keeps roughly the top 10%, so $s$ is the 90th percentile. DeepConf-high keeps roughly the top 90%, so $s$ is the 10th percentile.
  3. Generate with early stopping. For each new trace, track group confidence over the most recent window as tokens come out. The moment it drops below $s$, kill the trace. Its tokens are spent but you stop spending more, and it doesn't vote.

The logic of step 3: a finished trace's lowest group confidence is at most the group confidence of any window along the way. So if the current window is already below $s$, the trace's final score will be below $s$ too, and offline filtering would have discarded it anyway. Killing it now gives the same answer as generating it fully and then filtering. That's a neat argument, and it only holds because the score is a minimum. It wouldn't work for the average or the tail score.

There's a second, independent saving: adaptive sampling. After each trace finishes, compute the weighted share of the leading answer:

$$\beta = \frac{V(\hat{a})}{\sum_a V(a)}$$

If $\beta \ge \tau$ (the paper uses $\tau = 0.95$), stop sampling. Otherwise keep going until you hit the budget $B$ (512 in their runs). Easy problems where every trace agrees stop after a few dozen traces; hard ones use more of the budget.

Worked example: threshold from 16 warmup traces

Lowest group confidences of the 16 warmup traces, sorted:

rank01234567
value9.69.910.210.811.211.711.912.0
rank89101112131415
value12.212.312.512.612.813.013.113.4

Using linear interpolation (what numpy.percentile does by default), the $p$-th percentile sits at fractional rank $(16-1) \times p/100$.

  • DeepConf-low, 90th percentile: rank $15 \times 0.9 = 13.5$, halfway between 13.0 and 13.1, so $s = 13.05$.
  • DeepConf-high, 10th percentile: rank $15 \times 0.1 = 1.5$, halfway between 9.9 and 10.2, so $s = 10.05$.

With $s = 13.05$, only two of the warmup traces (13.1 and 13.4) would have survived. That's the aggressive setting: most new traces will be killed at some point. With $s = 10.05$, only the bottom two (9.6, 9.9) would have been cut.

Sixteen samples is not many for estimating a 90th percentile. The cutoff is basically "somewhere between the second-best and best warmup trace", and it'll move a lot from one question to the next just from sampling noise. The paper reports it works anyway; I'd still want to see the variance across seeds before relying on DeepConf-low.

Pseudocode: online DeepConf with adaptive sampling 
params: N_init = 16, budget B = 512, tau = 0.95, window n = 2048,
        keep fraction eta (0.10 -> DeepConf-low, 0.90 -> DeepConf-high)

# 1. warmup
W = generate N_init full traces
scores = [lowest_group_conf(t) for t in W]
s = percentile(scores, 100 * (1 - eta))
votes = {}
for t in W:
    if score(t) >= s: votes[t.answer] += score(t)   # warmup traces vote too

# 2. sampling with early stop
n_generated = N_init
while n_generated < B:
    t = new trace; window = deque(maxlen=n); min_g = +inf
    for each new token i:
        window.append(C_i)
        if len(window) == n:
            g = mean(window); min_g = min(min_g, g)
            if g < s:
                discard t; break           # killed, no vote
    else:
        votes[t.answer] += min_g           # finished normally
    n_generated += 1
    beta = max(votes.values()) / sum(votes.values())
    if beta >= tau: break                  # consensus reached
return argmax(votes)

In a real server the "for each new trace" loop runs as a batch of concurrent requests, not one at a time. Consensus is checked as traces finish.

6. What it saves

Token savings come from three places: killed traces stop partway, warmup is a fixed cost, and adaptive sampling can end the whole run before the budget. The estimator below is my own back-of-envelope model, not the paper's. It assumes every non-killed trace runs its full average length and killed traces die at a fixed fraction of the way through.

Token savings estimator

Share of post-warmup traces killed: 90%
Killed traces die after this fraction of full length: 35%
Traces sampled before consensus (β ≥ τ): 512

With the defaults (90% killed at 35% of the way, no early consensus) you save a bit over half. To get anywhere near the paper's 84.7% you need either earlier kills or adaptive sampling stopping well short of 512. That matches intuition: the biggest wins are on problems the model finds easy, where the vote is settled after a few dozen traces. On genuinely hard problems, where you most want the extra compute, savings shrink.

Reported numbers

The paper tests DeepSeek-8B, Qwen3-8B, Qwen3-32B, GPT-OSS-20B and GPT-OSS-120B on AIME 2024, AIME 2025, BRUMO 2025, HMMT 2025 and GPQA-Diamond. The headline case:

SettingGPT-OSS-120B, AIME 2025
cons@512 (plain majority)97.0%
DeepConf@512 (offline, filtered + weighted)99.9%
Online DeepConf token reduction vs. full parallel thinkingup to 84.7%

Keep the scale in mind. AIME 2025 has 30 problems. Going from 97.0% to 99.9% is a bit less than one problem's worth of accuracy, averaged over repeated runs. It's a real gain, but it's at the ceiling, and "up to" on the token savings means the best case across models and datasets. Gains elsewhere are smaller, and the aggressive 10% setting doesn't win everywhere. The authors are upfront that DeepConf-high is the safe default and DeepConf-low trades some risk for bigger savings.

7. Implementation

The method needs only per-token top-k logprobs, which vLLM and most inference servers already return. No training, no reward model, no extra forward passes. The authors describe it as a small change to vLLM: keep a running window of token confidences per request and finish the request early when the window mean drops below a per-question threshold. The sketch below shows the logic. It's not the authors' code, and the vLLM details (the shape of returned logprobs, how you'd hook a stop condition) vary by version.

Python sketch: confidence tracking and offline/online voting 
from collections import deque, defaultdict
import numpy as np

def token_conf(top_logprobs):
    """top_logprobs: list of k log-probabilities at one position."""
    return -sum(top_logprobs) / len(top_logprobs)

class GroupConfTracker:
    """Running window mean of token confidence. Return True to stop."""
    def __init__(self, threshold=None, window=2048):
        self.s, self.n = threshold, window
        self.buf, self.total = deque(), 0.0
        self.lowest = float("inf")

    def update(self, top_logprobs):
        c = token_conf(top_logprobs)
        self.buf.append(c); self.total += c
        if len(self.buf) > self.n:
            self.total -= self.buf.popleft()
        if len(self.buf) == self.n:
            g = self.total / self.n
            self.lowest = min(self.lowest, g)
            if self.s is not None and g < self.s:
                return True        # kill this trace
        return False

def weighted_vote(answers, scores, keep_frac=1.0):
    order = np.argsort(scores)[::-1]
    keep = order[: max(1, round(keep_frac * len(scores)))]
    V = defaultdict(float)
    for i in keep:
        V[answers[i]] += scores[i]
    best = max(V, key=V.get)
    return best, V[best] / sum(V.values())     # answer, beta

One edge case to watch: a trace shorter than the window never fills it, so it never gets a group score. You'd fall back to the mean over whatever tokens exist.

8. Where it breaks

The core assumption is that low confidence correlates with wrong answers. On average, for these models and these math benchmarks, it does. But the failure that matters is the other direction: a trace that is wrong and confident. Models trained hard with RL on math often produce fluent, assured derivations that contain a single wrong step. Nothing in the logprobs flags that step, because the model believed it. DeepConf will keep that trace and weight it up. If several traces share the same confident mistake, filtering makes the vote worse, not better.

Aggressive filtering also collapses diversity. Majority voting gets its power from independent errors cancelling out. Cut down to the top 10% and you might be voting with 50 traces that share a style, and possibly a blind spot. The paper's own results show the 10% setting sometimes lands below plain majority voting, which is exactly what you'd expect from this.

It needs logprobs. Many commercial APIs either don't expose them or expose only a few per position, and some reasoning models hide the reasoning tokens entirely. In practice this is a method for people running open-weight models on their own servers.

And it only applies where answers can be voted on. Math problems with a single boxed number are ideal. For open-ended writing or code, "majority answer" isn't well defined, and you'd need some other way to group traces before any of this helps.

None of that makes the paper less useful. The offline filter is a few lines of code on top of a vote you were already running, and the online version is one of the more practical test-time compute savings I've seen, because it needs nothing beyond what the server already computes. I'd use DeepConf-high by default and treat DeepConf-low as something to validate per model first.
