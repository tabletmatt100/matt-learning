Feature Engineering: Turning Raw Columns Into Signals Models Can Actually Split On

Raw database columns are designed for storage, not for machine learning geometry. When you hand a model raw columns like annual_debt, annual_income, zip_code, and application_hour ($0$ to $23$), the signal is technically in the table, yet different model families will trip over their own geometric blind spots trying to read it.

Consider the difference between a decision tree (XGBoost / LightGBM) and a linear model or neural network. A decision tree only cares about the sorted rank order of a column, so rescaling dollars into thousands or taking a logarithm $\ln(x)$ changes literally nothing for a tree—yet that same tree can only make horizontal or vertical axis-aligned cuts ($x_1 > c$), forcing it to carve a clumsy 10-step staircase just to approximate a simple diagonal ratio like Debt-to-Income ($x_1 / x_2$). Conversely, a linear model or k-NN classifier gets completely hijacked by unscaled dollar columns or skewed millionaire outliers, and thinks 11:00 PM ($h = 23$) and Midnight ($h = 0$) are $23$ hours apart unless you wrap time around a circle with $\sin$ and $\cos$.

Good feature engineering means matching each transformation to the model's exact blind spot—while guarding against the silent killer of tabular ML: target leakage when encoding high-cardinality categories like zip codes.

1. Why Trees Need Ratios While Linear Models Need Scaling & $\sin/\cos$

A decision tree splits data by testing whether a single column exceeds a threshold ($x_j > c$). Because a monotonic transformation like Z-score scaling ($z = \frac{x - \mu}{\sigma}$) or $\ln(1 + x)$ preserves the exact sorted order of rows, every split threshold on $\ln(x_2)$ separates the exact same rows as a threshold on $x_2$. Single-column scaling has zero effect on a tree. What trees struggle to learn on their own are ratios and differences between two columns ($x_1 / x_2$ or $x_1 - x_2$), because a diagonal line across two features requires dozens of axis-aligned staircase splits.

Worked Example (Why an interaction ratio collapses a staircase into 1 split):

Suppose loan applicants default whenever their Debt-to-Income ratio hits $0.50$:
• Applicant A (Default): Debt $x_1 = 20\text{k}$, Income $x_2 = 40\text{k} \implies \text{Ratio } r = \frac{20}{40} = \mathbf{0.50}$.
• Applicant B (Default): Debt $x_1 = 40\text{k}$, Income $x_2 = 80\text{k} \implies \text{Ratio } r = \frac{40}{80} = \mathbf{0.50}$.
• Applicant C (Paid): Debt $x_1 = 30\text{k}$, Income $x_2 = 100\text{k} \implies \text{Ratio } r = \frac{30}{100} = \mathbf{0.30}$.
On raw Debt $x_1$ alone, Applicant C ($30\text{k}$) sits right between A ($20\text{k}$) and B ($40\text{k}$), so no single threshold on Debt can separate $\{A, B\}$ from $C$. Once you engineer the ratio $r = x_1 / x_2$, a single split at $r \ge 0.50$ separates them cleanly in 1 node.

For linear models, neural networks, and k-NN, the priorities flip. Unscaled dollars ($40{,}000$) dwarf age ($40$) in Euclidean distance and L2 regularization, so you must standardize continuous columns with Z-score scaling using the training fold's mean $\mu_{\text{train}}$ and standard deviation $\sigma_{\text{train}}$, and apply $\ln(1 + x)$ to heavy-tailed dollar or count columns so a single millionaire outlier doesn't tilt the regression line.

And for periodic time columns like hour-of-day $h \in [0, 23]$, cyclical $\sin/\cos$ encoding maps the clock onto a 2D unit circle so 11:00 PM ($h = 23$) and Midnight ($h = 0$) sit right next to each other:

$$h_{\sin} = \sin\!\left(\frac{2\pi h}{24}\right), \qquad h_{\cos} = \cos\!\left(\frac{2\pi h}{24}\right)$$

2. High-Cardinality Categories & The Target Leakage Trap

When a categorical column only has a few unique values ($K \le 15$, like payment_type), one-hot encoding works cleanly by creating $K$ binary $0/1$ columns. When a column has thousands of levels ($K = 5{,}000$, like zip_code or merchant_id), one-hot encoding explodes into $5{,}000$ sparse columns.

Instead, Smoothed Target Encoding compresses a high-cardinality column into a single number by replacing each category $c$ with a blend of its historical target rate $\bar{y}_c$ (across $n_c$ rows) and the global prior $\bar{y}_{\text{global}}$, weighted by a smoothing pseudo-count $m$:

$$\hat{y}_c = \frac{n_c \bar{y}_c + m \bar{y}_{\text{global}}}{n_c + m} = \frac{\text{positives}_c + m \bar{y}_{\text{global}}}{n_c + m}$$

Why are smoothing ($m > 0$) and out-of-fold (OOF) calculation non-negotiable here? Suppose a rare zip code only appears once in your training set ($n_c = 1$), and that single applicant defaulted ($y_1 = 1$). If you compute naive in-fold target encoding without smoothing ($m = 0$), that row gets encoded as $\hat{y}_c = 1.00$—baking its own ground-truth label $y_1$ directly into its input feature (target leakage)! A decision tree will immediately split on $\hat{y}_c$ to get $100\%$ training accuracy and fail horribly in production. Computing target encoding out-of-fold ensures a row's own label $y_i$ is never included in its numerator, while smoothing $m$ pulls tiny categories back toward the safe global base rate $\bar{y}_{\text{global}}$.

The global fraud base rate is $\bar{y}_{\text{global}} = 0.10$ ($10\%$) and you use smoothing weight $m = 10$. A merchant has $n_c = 10$ past out-of-fold transactions, and $3$ of them were fraud ($\bar{y}_c = 0.30$). What is its smoothed target encoding $\hat{y}_c$?
