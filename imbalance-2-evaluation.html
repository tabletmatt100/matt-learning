Honest evaluation: splits, folds and leakage

TL;DR

  • Put an always-majority baseline row in every results table. On 1% fraud it scores 99% accuracy, 0 recall and PR-AUC 0.01.
  • Stratify every split. With 100 positives and 5 unstratified folds, a fold can get anywhere from about 13 to 28 of them.
  • Even stratified, recall on 20 positives has a standard error near 0.09. Report the spread, pool out-of-fold predictions, and don't crown a model for winning by one case.
  • If the data has time order or repeat customers, split by time or by group. Random row splits leak the future and the same card into validation.
  • The test set keeps the production class ratio. A 50:50 test set turns a precision of 0.20 into 0.96 without the model changing at all.
  • Resample only inside training folds, using an imbalanced-learn pipeline. Oversampling before the split puts exact copies of validation positives into training.

1. The running example and the baseline row

Same setup as the rest of the series: a card-fraud model scored on 10,000 transactions, 100 of them fraud (1%, a 99:1 ratio). At its chosen threshold it gets TP = 80, FN = 20, FP = 320, TN = 9,580. If those numbers are new to you, Part 1 builds the confusion matrix and the metrics from scratch.

Most of the damage I've seen from imbalance isn't from a bad model. It's from evaluation that lies, so you tune toward the wrong thing. This part is about making the numbers trustworthy before you spend any time on weights, resampling or thresholds.

Always include the do-nothing model

The first thing I add to any results table is a majority-class baseline: a model that predicts "legit" for every transaction. In scikit-learn that's DummyClassifier. It costs one line and it stops everyone (including me) from celebrating a number that a constant beats.

Where the fraud model's row comes from.

Accuracy $= (80 + 9580)/10000 = 0.966$. Precision $= 80/(80+320) = 0.200$. Recall $= 80/100 = 0.800$.

F1 $= 2(0.2)(0.8)/(0.2+0.8) = 0.32$. Specificity $= 9580/9900 = 0.9677$, so balanced accuracy $= (0.8 + 0.9677)/2 = 0.884$.

MCC $= \dfrac{80 \cdot 9580 - 320 \cdot 20}{\sqrt{400 \cdot 100 \cdot 9900 \cdot 9600}} = \dfrac{760{,}000}{1{,}949{,}769} = 0.390$.

The baseline's precision is 0/0 because it never flags anything. sklearn returns 0 with a warning (the zero_division argument controls this). A constant score gives PR-AUC equal to the base rate, 0.01, and ROC-AUC of exactly 0.5.

The fraud model has lower accuracy than doing nothing. That's fine. It traded 320 false alarms for 80 caught frauds. The baseline row makes that trade visible instead of embarrassing.

2. Stratify your splits

With 100 positives and a random 80/20 split, the test set gets on average 20 positives, but it could easily get 13 or 28. With 5-fold CV, each fold has roughly 20, and the variance between folds will be large. Stratified splitting forces each fold to have the same positive rate as the whole. In scikit-learn it's StratifiedKFold and train_test_split(..., stratify=y). There is no reason not to do this.

Where "13 to 28" comes from. Picking 2,000 test rows out of 10,000 at random, the number of frauds that land in the test set follows a hypergeometric distribution with population 10,000, 100 "successes" and 2,000 draws.

Mean $= 2000 \times 100/10000 = 20$.

Standard deviation $= \sqrt{2000 \times 0.01 \times 0.99 \times \tfrac{10000-2000}{10000-1}} = \sqrt{19.8 \times 0.80008} = \sqrt{15.84} = 3.98$.

Summing the exact probabilities, 95% of random splits put between 13 and 28 frauds in the test set. About 8% of splits give 14 or fewer. A stratified split gives exactly 20, every time.

That spread matters for more than recall. A fold with 14 positives and one with 26 have different base rates (0.7% vs 1.3%), so their precision and PR-AUC are not even measuring the same thing. Stratification removes that source of noise for free.

3. How noisy is recall on 20 positives?

Even stratified, 20 positives per fold means a recall estimate jumps by 0.05 every time one case flips. That's not a rounding detail. It means two models that are genuinely identical will regularly differ by 0.05 or 0.10 on a single fold.

Treat each fraud in the fold as a coin flip that the model catches with probability $r$. The number caught is binomial, so the standard error of the recall estimate on $n$ positives is:

$$\text{SE}(\hat r) = \sqrt{\frac{\hat r\,(1-\hat r)}{n}}$$

Recall 0.8 on one fold of 20 positives.

$\text{SE} = \sqrt{0.8 \times 0.2 / 20} = \sqrt{0.008} = 0.089$.

Simple (Wald) 95% interval: $0.8 \pm 1.96 \times 0.089 = 0.8 \pm 0.175$, so $[0.625,\ 0.975]$.

The Wilson interval behaves better at small $n$. With $z = 1.96$, $z^2 = 3.8416$:

Denominator $d = 1 + z^2/n = 1 + 3.8416/20 = 1.1921$.

Centre $= (\hat r + z^2/2n)/d = (0.8 + 0.0960)/1.1921 = 0.7517$.

Half-width $= \dfrac{z}{d}\sqrt{\dfrac{\hat r(1-\hat r)}{n} + \dfrac{z^2}{4n^2}} = \dfrac{1.96}{1.1921}\sqrt{0.008 + 0.0024} = 1.6442 \times 0.1020 = 0.1677$.

Wilson 95% interval: $[0.584,\ 0.919]$. The true recall could plausibly be anywhere from below 0.6 to above 0.9. That's one fold.

Precision is a little steadier per fold only because its denominator is bigger: 80 flagged per fold, 16 of them fraud, gives $\sqrt{0.2 \times 0.8 / 80} = 0.045$. Still not small next to 0.2.

What I do about it

Report the spread across folds, not just the mean. If positives are scarce I use repeated stratified CV (say 5 folds times 10 repeats) so the result doesn't hinge on one lucky shuffle. And I compute the headline metrics once on the pooled out-of-fold predictions: every one of the 100 positives gets scored exactly once by a model that never saw it.

Pooling helps. 80 of 100 positives caught across all five validation folds: $\text{SE} = \sqrt{0.16/100} = 0.040$, Wilson interval $[0.711,\ 0.867]$. Less than half the width of the single-fold interval, using the same data.

When comparing two models, compare them on the same folds and look at where they disagree. On one 20-positive fold, a 0.85 vs 0.80 recall gap is a single fraud. McNemar's test on the cases where exactly one model is right is the standard tool, and it will tell you that one or two disagreements prove nothing.

Code: repeated stratified CV and pooled out-of-fold scores 
import numpy as np
from sklearn.model_selection import (StratifiedKFold, RepeatedStratifiedKFold,
                                     cross_validate, cross_val_predict)
from sklearn.metrics import recall_score, average_precision_score
from sklearn.dummy import DummyClassifier

rcv = RepeatedStratifiedKFold(n_splits=5, n_repeats=10, random_state=0)
res = cross_validate(model, X, y, cv=rcv, scoring=["recall", "average_precision"])
r = res["test_recall"]
print("recall per fold: mean %.3f  sd %.3f  min %.2f  max %.2f"
      % (r.mean(), r.std(), r.min(), r.max()))

# baseline row, same folds
base = cross_validate(DummyClassifier(strategy="most_frequent"), X, y, cv=rcv,
                      scoring=["recall", "average_precision"])

# pooled out-of-fold predictions (needs a single partition, not a repeated one)
skf = StratifiedKFold(n_splits=5, shuffle=True, random_state=0)
oof = cross_val_predict(model, X, y, cv=skf, method="predict_proba")[:, 1]
print("pooled PR-AUC", average_precision_score(y, oof))
print("pooled recall", recall_score(y, oof >= 0.5))

cross_val_predict refuses repeated splitters because each row would get several predictions. Run it once per seed if you want pooled scores for each repeat.

Aside: why the standard deviation across 50 folds still understates the uncertainty

With repeated CV you get 50 scores, and it's tempting to quote the standard error of their mean as $\text{sd}/\sqrt{50}$. Don't. The folds share training data, and the repeats reuse the same 100 positives, so the 50 scores are strongly correlated. Bengio and Grandvalet (2004) showed there is no unbiased estimator of the variance of k-fold CV. Repeating reduces the noise from how you shuffled; it can't reduce the noise from having only 100 frauds. The pooled binomial interval above is a more honest floor on the uncertainty.

On a single stratified fold with 20 frauds, the model catches 16 (recall 0.80). Using the simple binomial standard error, what's the approximate 95% interval?

4. Time-based splits and drift

If you have time structure (fraud usually does), split by time instead of at random, and accept that the positive rate will drift between folds. That drift is real and you want to see it. A random split lets the model train on November's fraud ring and get validated on October's transactions from the same ring. In production it never gets to see the future.

sklearn's TimeSeriesSplit gives expanding-window folds: train on months 1 to 3, validate on 4; train on 1 to 4, validate on 5; and so on. You lose stratification, which is the point. Each validation fold has whatever fraud rate that month had.

Same model, three months. Hold recall at 0.80 and FPR at $320/9900 = 0.0323$, and score 10,000 transactions per month while the fraud rate drifts:

MonthFraud rateTPFPPrecision
June0.8%$0.8 \times 80 = 64$$0.0323 \times 9920 = 321$$64/385 = 0.166$
July1.1%$0.8 \times 110 = 88$$0.0323 \times 9890 = 320$$88/408 = 0.216$
August1.4%$0.8 \times 140 = 112$$0.0323 \times 9860 = 319$$112/431 = 0.260$

Precision moves from 0.17 to 0.26 with no change to the model. A random split would average this away and hand you a single 0.2 that no month actually had.

Fraud has a second time problem: label delay. A fraudulent transaction often isn't labelled fraud until the cardholder disputes it, weeks later. If you cut training at March 31 and pull labels on April 2, late-March fraud is still sitting in the data labelled "legit". I leave a gap between the end of training and the start of validation, and only use rows whose labels have had time to settle.

Code: time-ordered folds with a gap 
from sklearn.model_selection import TimeSeriesSplit

df = df.sort_values("timestamp")          # TimeSeriesSplit trusts the row order
X, y = df[features].to_numpy(), df["is_fraud"].to_numpy()

tss = TimeSeriesSplit(n_splits=5, gap=5000)  # gap is in rows, not days
for k, (tr, va) in enumerate(tss.split(X)):
    print(k, "train", len(tr), "valid", len(va),
          "valid fraud rate %.3f%%" % (100 * y[va].mean()))

gap counts rows, so convert your label-maturity window into a row count (or build the folds by date yourself). The printed fraud rate per fold is the drift you should expect in production.

On a year of transactions, stratified random 5-fold CV gives PR-AUC 0.62. Time-ordered folds (train on earlier months, validate on the next) give 0.41. Which number should go in the report?

5. Keep each card on one side of the split

Fraud rarely comes one transaction at a time. A stolen card gets used several times in an afternoon, and those rows look alike: same card, same merchant category, same odd hour. If a random split puts some of them in training and some in validation, the model can score well by recognising the card instead of the fraud. That's group leakage, and it's very common.

How likely is it? Suppose the 100 frauds come from 25 compromised cards, 4 rows each, and you use 5-fold CV on rows. Take any fraud row in a validation fold. Each of its 3 siblings lands in a training fold with probability about $4/5 = 0.8$.

$P(\text{no sibling in training}) = 0.2^3 = 0.008$, so $P(\text{at least one sibling in training}) = 1 - 0.008 = 0.992$.

About 99 of your 100 validation frauds have a twin the model trained on. Your CV recall is measuring "have I seen this card before?"

The fix is to split on the entity, not the row: GroupKFold keeps every row with the same card_id in one fold. With imbalance you also want stratification, which is what StratifiedGroupKFold does (as well as it can; whole groups can't be split to hit the ratio exactly). Which key to group on is a judgement call: card, customer, device, merchant. I pick the one that production will see fresh. 

from sklearn.model_selection import StratifiedGroupKFold, cross_validate

sgkf = StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=0)
scores = cross_validate(pipe, X, y, groups=df["card_id"], cv=sgkf,
                        scoring=["average_precision", "recall"])

Spot the bug. A team reports CV recall of 0.95 using StratifiedKFold on rows. In production, recall is 0.55. Their notes say: "Most fraud bursts are 3 to 6 transactions on the same card within an hour. Features include card-level rolling counts." What's the most likely cause?

6. Never resample the test set

The test set should look like production. If production has 1% fraud, so does the test set. If you balance the test set to 50:50, precision goes way up (fewer negatives to generate false positives), and you'll ship a model whose precision in the wild is a fraction of what you reported. Accuracy on a balanced test set is just balanced accuracy in disguise, and PR-AUC becomes incomparable to anything in production.

Recall and FPR don't depend on the class ratio, because each is computed within one class. Precision mixes the two classes, so it does:

$$\text{precision} = \frac{r\,\pi}{r\,\pi + \text{FPR}\,(1-\pi)}$$

where $r$ is recall and $\pi$ is the share of positives in whatever set you're scoring.

Same model, two test sets. Recall 0.80, FPR $= 320/9900 = 0.0323$.

Real 1% test set: $\dfrac{0.8 \times 0.01}{0.8 \times 0.01 + 0.0323 \times 0.99} = \dfrac{0.008}{0.008 + 0.032} = 0.200$.

Balanced test set, 100 frauds and 100 legit: TP $= 80$, FP $= 0.0323 \times 100 = 3.2$. Precision $= 80/83.2 = 0.961$.

Same model, same recall, same FPR. The balanced test set reports precision 0.96; production delivers 0.20. Analysts expecting roughly 1 false alarm per 25 alerts will get 4 in every 5.

Accuracy on the balanced set: $0.5 \times 0.8 + 0.5 \times 0.9677 = 0.884$, which is exactly the balanced accuracy from section 1. A random scorer's PR-AUC baseline jumps from 0.01 to 0.5.

7. Resample only inside the training folds

This is the classic leakage bug. If you run SMOTE (or random oversampling) on the full dataset and then do cross-validation, synthetic points made from a validation-fold positive end up in the training fold. Duplicated points are worse: the exact same row appears on both sides. The model has effectively seen the answers, and CV scores come out inflated, sometimes wildly. (Whether to resample at all is Part 5's question. This section is only about where it goes.)

Counting the copies. Oversample the 100 frauds to 3 copies each (300 fraud rows), then run 5-fold CV on the result. Each validation fold holds about $300/5 = 60$ fraud rows.

Pick one of them. Its 2 copies each land in training with probability about 0.8. $P(\text{both copies also in validation}) = 0.2^2 = 0.04$.

So $1 - 0.04 = 96\%$ of validation fraud rows, about 57.6 of 60, have an identical twin in training. A model that memorises (a deep tree, k-NN, a big boosted ensemble) gets them right for free.

Balance fully to 99:1 and every positive has 98 twins: $1 - 0.2^{98}$ is 1 to any precision you care about. All 1,980 validation fraud rows are memorised, and they represent just 100 distinct transactions.

SMOTE doesn't produce exact copies, but each synthetic point sits on a line between two real positives. When one end of that line is a validation positive, the training set contains a point within a fraction of a neighbour-distance of it. It's a softer leak and still a leak.

Oversample-then-split leak counter

100 real frauds. Random oversampling gives each one $m$ copies in total, and then the data is split into $k$ folds at random (the bug). Each square is 1% of the validation fold's fraud rows; filled squares have an exact copy sitting in training.

3

The fix is to make resampling a pipeline step so it runs fresh on each training fold and never touches the validation fold. imbalanced-learn ships a Pipeline that does exactly this (the sklearn one won't accept samplers).

Code: leak-free resampling inside cross-validation 
from imblearn.pipeline import Pipeline          # not sklearn.pipeline
from imblearn.over_sampling import SMOTE
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import StratifiedKFold, cross_validate

pipe = Pipeline([
    ("scale", StandardScaler()),
    ("smote", SMOTE(k_neighbors=5, random_state=0)),  # fit_resample on train folds only
    ("clf",   LogisticRegression(max_iter=1000)),
])

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=0)
scores = cross_validate(
    pipe, X, y, cv=cv,
    scoring=["average_precision", "f1", "matthews_corrcoef"],
)
for k, v in scores.items():
    if k.startswith("test_"):
        print(k, v.mean().round(3), "+/-", v.std().round(3))

# WRONG (leaks):
# X_res, y_res = SMOTE().fit_resample(X, y)
# cross_validate(LogisticRegression(), X_res, y_res, cv=cv)

The imblearn pipeline only calls the sampler during fit. At predict time it is skipped, so validation and test data pass through untouched.

The same rule covers anything fitted to data: the scaler, imputer, target encoder, feature selector. Fitting them on all the rows is a quieter version of the same preprocessing leak. Put them in the pipeline too, and if you tune hyperparameters, tune the whole pipeline with GridSearchCV and keep a final holdout it never touches.

Code: tuning the sampler and the model together, without leaking 
from sklearn.model_selection import GridSearchCV, train_test_split

X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.2,
                                          stratify=y, random_state=0)
grid = GridSearchCV(
    pipe,
    param_grid={"smote__sampling_strategy": [0.1, 0.25, 0.5],
                "clf__C": [0.1, 1, 10]},
    scoring="average_precision",
    cv=StratifiedKFold(5, shuffle=True, random_state=0),
)
grid.fit(X_tr, y_tr)                    # SMOTE refit inside every inner fold
print(grid.best_params_, grid.best_score_)
print("holdout PR-AUC", average_precision_score(
      y_te, grid.predict_proba(X_te)[:, 1]))   # test set: natural 1%, used once

If you also want an unbiased estimate of the tuning process itself, wrap the grid search in an outer CV loop (nested CV). For most fraud projects a time-later holdout does the same job more convincingly.
